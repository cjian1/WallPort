# M7.5 原生 Steam 客户端：一次登录、不依赖 SteamCMD

用户选了产品计划里的 M7.5：**自己实现 Steam 客户端协议**，替换掉 SteamCMD。

## 为什么做

两件事逼着走这条路：

1. **只需要确认一次。** 现在 M7 用两套独立的 Steam 登录：Steam 社区的网页会话（订阅 / 取消订阅 / 我的订阅）
   和 SteamCMD 的客户端会话（下载）。Steam 把它们当两台不同设备，第一次要分别在手机上确认两次。
2. **SteamCMD 只有 x86_64 版**，靠 Rosetta 运行，macOS 28 起会断。

## 先查清楚的三件事（2026-09-29）

**两套会话不能互换**，所以"少确认一次"只能靠砍掉其中一套：

- SteamCMD 缓存的凭据在 `~/Library/Application Support/Steam/config/config.vdf` 的 `ConnectCache`，
  是一枚 504 字节的**加密二进制块**（不是 JWT，解出来没有可打印内容），换不出网页用的令牌；
- 官方 Web API 里有 `ISteamRemoteStorage/EnumerateUserSubscribedFiles`、`SubscribePublishedFile`、
  `UnsubscribePublishedFile`，但它们要的是**发行商 API Key**，文档原文：
  "requires a publisher API key ... MUST be called from a secure server, and can never be used directly by clients"
  ——客户端直连这条路被 Valve 自己堵死了；
- 反过来"只用网页会话下载"也不行：WE 的创意工坊条目 `file_url` 是空的（实测 3807008481、3169364633），
  内容在 UGC depot 里，要客户端协议拿清单和 depot 密钥才能从 CDN 取。

**CM 可以用同一次认证的令牌登录。** Valve 的 `steammessages_clientserver_login.proto` 里
`CMsgClientLogon` 有 `access_token`（字段 108）。实测下来要点是：认证会话本身要在 CM 上做（网页登录拿到的令牌
CM 不认），`access_token` 字段里填的是 **refresh token**，消息头部要带这个账号的 SteamID——这样一次确认就覆盖
订阅、我的订阅和下载，这正是 M7.5 的立足点（细节见后面的过程记录）。

**WebSocket 传输的信封格式（本机实测）。** CM 服务器列表用公开接口
`ISteamDirectory/GetCMListForConnect?v=1&cellid=0&cmtype=websocket` 取，形如
`wss://cmp1-iad1.steamserver.net:27018/cmsocket/`；消息信封是
`[消息号 4 字节小端][头部长度 4 字节小端][CMsgProtoBufHeader][消息体]`，其中
**消息号要带 `0x80000000`（protobuf 位）**，外面**不需要** TCP 那层 `[长度]["VT01"]` 包装。
这四条组合是逐个试出来的：只有"带 protobuf 位、不包 VT01"这一种能收到回应（其余三种等消息超时），
正确的写法 0.3 秒就返回 `ClientLogOnResponse`（751）。命令：`WallpaperTool steam-cm --framings`。

## 2026-09-29 审查后的修正

对着 Valve 的 `.proto`（SteamDatabase/Protobufs）逐字段核对、再按应用里的真实用法过了一遍，改了这些：

- **订阅 / 取消订阅的编号类型写错了**：`CPublishedFile_Subscribe_Request.publishedfileid` 是 `uint64`（varint），
  代码按 `GetDetails` 那样写成了 `fixed64`——Steam 的解析器会把类型不对的字段当成不认识的丢掉，等于没传编号，
  应用里点"订阅 / 取消订阅"会失败。单元测试当时是照着错误写法写的（所以一直是绿的），已改成按 `.proto` 断言；
- **账号密码登录的 SteamID 读错了**：`BeginAuthSessionViaCredentials` 回包的 `steamid` 是 `uint64`（varint），
  代码按 `fixed64` 读，永远得到 0；交验证码（`UpdateAuthSessionWithSteamGuardCode`）时就带着 0 发出去。测试同样是照错误写法写的，已改；
- **同一条连接上的并发请求会互相吞回包**：原来的收包是"谁先等谁拿"，拿到别人的回包就丢掉，另一个请求只能等到超时。
  应用里读订阅列表、下载、取消订阅会并发，这会表现成随机的"等回包超时"。现在先登记"在等哪个 job / 哪种消息"再发，
  收到的消息按 `jobid_target` / 消息号分发（实机核对：三个并发的未登录调用，CM 用一个 Multi 回来，各拿各的）；
- **登录后的连接没有心跳、断了也不会重连**：应用里一条连接要用很久，原来断了（CM 回收、睡眠、换网络）以后每个操作都失败，
  直到重启 App。现在登录后按 `heartbeat_seconds` 发 `CMsgClientHeartBeat`（EMsg 703），操作发现连接断了会用会话里的
  refresh token 重新登一次再试一次；只有 Steam 明确不认令牌（EResult 5/15/26/27…）才要求重新登录；
- **"只登录一次"在重启后不成立**：原来只有切到创意工坊页才去恢复会话，而且同时就弹了登录框；在壁纸库设置里点"取消订阅"
  会直接说"要先登录"。现在 App 启动时同步读出会话、直接当作已登录，后台再连 CM；
- **账号密码登录的几处卡死**：交验证码之后界面停在转圈、填错了看不到原因也不能重填；等邮件验证码超过约一分钟未登录连接被 CM 回收后，
  交验证码 / 轮询直接失败（扫码那条有重连、密码这条没有）；点"取消"以后轮询还在后台连发请求（`try? Task.sleep` 吞掉了取消）。都已修；
  扫码登录跟着 `new_challenge_url` 换二维码；拿到令牌后改用新连接登 CM（和命令行实测通过的做法一致），登录用的连接不再顶掉已登录的那条；
- **下载**：清单里的目录条目（`flags` 64）和 Windows 路径分隔符 `\` 没处理（WE 的内容都是在 Windows 上传的，网页壁纸常有子目录，
  会建出名字里带反斜杠的文件或者直接失败）；符号链接条目跳过；分块直接写到文件偏移，不再把整个文件攒在内存里（视频壁纸几百 MB）；
  整件先下到 `.downloading-<编号>`，成功后才换进下载目录——失败不留半截项目，更新时旧版本多出来的文件也不残留；
- 其它：protobuf 长度前缀越界时不再可能整数溢出崩溃；WebSocket 单帧上限从默认 1 MB 放宽；每条连接的 URLSession 关闭时释放；
  删掉 `Workshop.swift` 里 SteamCMD / 网页会话时代没人用的代码和只测它们的测试（下载目录的位置不变，老用户已下的壁纸照常识别）；
  README 里的 `steam-cm --keychain` 已经不存在（会报"认不出的参数"），改成现在的写法。

## 规矩与风险

- 消息定义只来自 **Valve 自己随客户端发布的 `.proto`**（`SteamDatabase/Protobufs` 镜像）与公开资料；
  EMsg 编号取自 MIT 许可的公开对照表；**不阅读、不参考 GPL / AGPL 实现**（沿用产品计划第 6 节）；
- 自己实现客户端协议比 SteamCMD 更深入 Steam 用户协议的灰区，这一条是用户拍板接受的
  （见 `docs/M7-创意工坊.md` 的"取舍"）。账号密码登录时，密码只用 Steam 给的 RSA 公钥加密后发给 Steam，
  不存盘、不写日志；之后只用令牌（refresh token）登录；
- SteamCMD 那条路已经删掉（M7.5-4），要退回只能从 git 历史里找。

## 还没验证 / 已知问题

- 订阅 / 取消订阅：已实机核对（`list_type = 1`，见上）；
- 应用里的账号密码登录已实机成功（2026-09-29）；扫码登录只在命令行实测过；
- 心跳（EMsg 703）和"断线重连后再试一次"只在假的 CM 上测过，真机长时间挂着的表现还没看；
- 清单里的目录条目 / `\` 分隔符是按 `.proto` 的 `flags`、`linktarget` 字段和 Windows 上传的事实做的防御，本机两件样本都是平铺文件，
  还没用带子目录的网页壁纸实机下过；
- 匿名登录被 Steam 拒（`EResult 5`）。只是验证帧格式的探针，不影响令牌登录路线。

## 登录走 CM（`steam-cm --cm-auth`）的过程记录

### 先修掉"未登录服务调用没有回应"（2026-09-29，CMsgMulti）

之前一直以为"未登录的服务调用没回应"（见 commit 52ded5d），今天查清楚了：**回应其实来了**，
只是裹在 `CMsgMulti`（EMsg 1）里——CM 会把好几条消息 gzip 压成一个包发过来，载荷是
`[长度 4 字节小端][完整消息信封]` 串起来的（`receivedTypes` 里只看到一个 `1` 就是它）。
参考实现的 `WebSocketCMTransport._processMultiMsg` 就是干这个的（`Zlib.gunzip` + 按长度切）。

修完立刻见效：

```bash
swift run WallpaperTool steam-cm --cm-auth-key <账号>
# → ✓ 未登录服务调用成功：账号 … 的 RSA 模长 2048 位，指数 010001，时间戳存在 true
```

代码在 `CMEnvelope.multiMessages`（拆包）和 `Gzip.decompress`（用系统 libz 解 gzip/zlib）；
连接层收到 Multi 会自动拆开再按普通消息派发，改动只在 `SteamCMConnection.deliver`。
这一条同时解释了 8 月底以来"服务方法调不通"的所有现象。

### 两条登录路

### 2026-09-29 关键结论：**令牌登 CM 成了，差的是消息头部的 steamid**

#### 整条原生链路已经跑通（同一次扫码登录，逐字节一致）

```
① 登 CM（扫码会话的 refresh token + 头部带 steamid）：成功，cell 64
② PublishedFile.GetDetails：Ronova - Face Check｜94.7 MB｜清单 6176428963886766760
③ ContentServerDirectory.GetServersForSteamPipe：25 台 CDN
④ GetDepotDecryptionKey：32 字节
⑤ GetManifestRequestCode：11605092192252668357
⑥ 从 CDN 取清单（zip 容器 + 加密文件名用 depot 密钥解开）：3 个文件、92 个分块
⑦ 92 个分块 / 94.7 MB 下完 → 和 SteamCMD 下好的那份**逐字节一致**
```

这一趟又踩到两个只有真机才会遇到的东西：

- **CDN 上的清单是 zip（`PK\x03\x04`）容器**，不是分块那种 `VSZa`；而且**文件名是加密的**
  （`ContentManifestMetadata.filenames_encrypted` = 4 为真时，`FileMapping.filename` 里放的是
  base64 的密文，用 depot 密钥按同一套 AES 解开、取第一个 0 字节之前的部分当名字）。
  SteamCMD 留在 `depotcache/` 里的那份是已经解开的明文，所以之前看不出来；
- **`CMsgMulti` 里会混着"非 protobuf"的老式消息**（头部是 `[消息号 4][头部长 1 字节 = 36]…`）：
  一条 Multi 里只要有这么一段，按 protobuf 去解就会报"头部长得超出消息"，整条 Multi 全丢——
  而 751 常常就在那条 Multi 里（表现成"登录超时"）。现在这种消息按"不认识"跳过，不报错。

之前所有"令牌被 CM 拒（EResult 5）"的尝试，根因是 `CMsgClientLogon` 的**消息头部 `steamid` 发了 0**。
实测（用 `steam-cm --cm-auth-qr` 扫码拿到的 refresh token，8 种字段组合 + 头部两种写法逐个试）：

| 组合 | 结果 |
|---|---|
| `access_token` = refresh token，头部 `steamid` = **0** | ✗ EResult 5（账号或密码不对） |
| `access_token` = refresh token，头部 `steamid` = **令牌 `sub` 里的 SteamID** | **✓ 成功**，SteamID 76561198419273616 |
| 同上 + 带 `account_name` | ✓ 成功（带不带都行） |
| 同上 + 不带 `machine_id` | ✓ 成功 |
| `access_token` = access token（而不是 refresh token） | ✗ EResult 15（AccessDenied） |

也就是说"一次确认覆盖订阅 + 下载"这条路线**成立**：

- 令牌要 `iss = "steam"`、`aud` 含 `client`（扫码拿到的 refresh token 是 `aud [client,web,renew,derive]` ✓）；
- `CMsgClientLogon.access_token`（字段 108）填的是 **refresh token**；
- **头部的 `steamid` 必须是这个账号的 SteamID**（参考实现 steam-user 从令牌 `sub` 里取；现在我们
  `SteamCMConnection.logOn` 会自动从令牌里解析，不用调用方操心）；
- `access_token` 那枚令牌给 CM 会得到 EResult 15，别拿错。

代码：`SteamCMConnection.logOn` 里自动取头部 SteamID；`SteamJWT` 负责解析令牌里的 `iss/aud/sub`。
复现命令（令牌存在 `/tmp/wallport-tokens.json` 时可离线反复试）：

```bash
swift run WallpaperTool steam-cm --token-file /tmp/wallport-tokens.json
```

（当时还猜过"短时间内反复登 CM 会被静默限流"，后来证明是错的：那些"连上之后没有回应"其实是
下面说的"`CMsgMulti` 里混着非 protobuf 老式消息、整条被丢掉"，751 就在里面。令牌本身可以反复用。）

**（推荐）扫码登录，不用密码**：

```bash
swift run WallpaperTool steam-cm --cm-auth-qr --wait 300 --qr /tmp/qr.png
# 用手机 Steam App 扫 /tmp/qr.png（或点开打印出来的 https://s.team/q/…）→ 确认登录
```

**账号密码登录**（密码只在终端里输入、不回显）：


## M7.5-3 的进展（2026-09-29）：**下载这条路已经打通并逐字节验证**

先纠正上一节的两处猜测：

1. **分块是加密的**（不只是压缩）：密钥就是 depot 解密密钥，格式是
   `[AES-ECB 加密过的 IV 16 字节][AES-CBC 密文（PKCS#7 填充）]`。前 16 字节要用 depot 密钥按
   AES-ECB 解出 IV，再拿它做 AES-CBC——少了这一步，整块解不开（`EResult` 全是乱的）。
2. **容器不是 LZMA，是 `VSZa`（zstd）**：`"VSZa" + [解压数据的 CRC32 小端] + zstd 数据 +
   [同一个 CRC32][解压后长度小端][4 字节 0]["zsv"]`。zstd 随项目编译（`Vendor/zstd`，
   BSD-3-Clause），macOS 系统里没有 libzstd。旧内容的 `VZa`（LZMA）和 `PK`（zip）容器先只认出来、
   明确报错——本机拿到的 Wallpaper Engine 分块 123/123 都是 `VSZa`。

这条路不需要登录也能验证完（分块地址直接 200，前缀不带令牌），所以是**实机跑通**的：

```bash
# depot 密钥是 Steam 自己缓存的（config.vdf 的 depots/431960/DecryptionKey）；
# 应用里应该走 CM 的 GetDepotDecryptionKey，而不是读这个文件
WallpaperTool steam-ugc "/Users/…/Steam/depotcache/431960_6176428963886766760.manifest" /tmp/out \
    --depot 431960 --host steampipe.akamaized.net --key-env WALLPORT_DEPOT_KEY \
    --verify "/Users/…/Steam/steamapps/workshop/content/431960/3807008481"
# → 92 个分块、3 个文件、94.7 MB，15 秒，和 SteamCMD 下好的那份逐字节一致
```

两件壁纸都对上了（94.7 MB 与 30.5 MB，123 个分块，SHA-1 与容器里的两个 CRC32 全部通过），
所以"原生下载"这一块只剩**取清单**那一步要真的登录才能验（清单不带请求码是 401）。

### 令牌受众：两次实机验证的结论（2026-09-29）

| 登录时用的 platform_type / website_id | 令牌当网页 Cookie | 令牌登 CM | 用它的 refresh_token 换网页令牌 |
|---|---|---|---|
| 3（MobileApp）/ Mobile | ✅ HTTP 200、读到 30 个订阅 | ❌ EResult 5（账号或密码不对） | ✅（现有刷新逻辑就是这么做的） |
| 1（SteamClient）/ Client | ❌ 网页说没登录 | ❌ EResult 5（四种字段组合都试了：账号名、只带令牌、加 machine_id、加机器信息） | ❌ x-eresult 15（AccessDenied） |

所以"客户端平台登录、再换网页令牌"这条路走不通：那种 refresh_token 换不出网页令牌。
下一组要试的是 **platform_type = 1 + website_id = Community**（让令牌的网站是社区，看网页和 CM 是否都认它）；
如果也不行，就回到 3 + Mobile 并换别的办法把令牌喂给 CM。

### 权威对照：参数该怎么配（node-steam-session，MIT）

它把三件事写得很清楚（`src/LoginSession.ts`）：

1. **平台和网站是配对的**：`SteamClient → website_id "Client"`、`WebBrowser → "Community"`、
   `MobileApp → "Mobile"`（`_defaultWebsiteId`）。所以 platform_type 1 要配 "Client"，
   配 "Community" 是错的（试过，一样被拒）；
2. **refresh token 的 `aud` 声明了受众**：`client` / `mobile` / `web`，换网页 Cookie 时它要求
   audience 和会话的平台一致——这解释了为什么我们拿客户端平台的 refresh token 调
   `GenerateAccessTokenForApp` 会得到 AccessDenied（x-eresult 15）：那个接口是给 MobileApp
   那种会话换"app 令牌"用的；
3. **SteamClient 平台的会话默认走 WebSocket CM 传输**（`WebSocketCMTransport`），
   而不是 Web API。我们的认证会话是通过 HTTPS（WebApiTransport）做的——很可能就是这一点，
   让我们拿到的客户端令牌不被 CM 的登录接受（EResult 5）。

**下一步（据此调整）**：把认证会话本身也改到 CM 上做——`Authentication.BeginAuthSessionViaCredentials#1`
等都是统一服务方法，而我们在 M7.5-2 里已经能把服务方法调到 CM 上了；用它拿到的令牌再登 CM，
才是"一次确认覆盖两边"的正路。
