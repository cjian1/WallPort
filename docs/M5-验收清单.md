# M5 效果与粒子：验收清单

计划里的验收标准：**创意工坊热门场景中至少 60% 可正常渲染**（M6 与 M5 合并验收时提到 85%）。

## 先说清楚这次验收能证明什么

- **样本**：用户本机 `~/wp` 里的 24 个场景（用户自己订阅的，不是"订阅量前 100"的榜单）。结论只对这个样本成立，
  要对"热门场景"下结论，需要按榜单另取一批；
- **没有 WE 的参照截图**：Windows 上 WE 实际渲染的画面一张都没有。24 个里只有 Lucy（3521337568）是 Everyone 分级，
  人工逐项看过；其余 23 个按项目规则只做像素统计，不看画面；
- 所以这里的"正常渲染"是按下面三条可以客观核对的标准判断的，不等于"和 WE 一模一样"：
  1. 能构建、能渲染，没有报错；
  2. 场景里的内容都有对应的实现，没有被跳过、会改变画面的东西；
  3. 带特效或粒子的场景确实在动（第 0 秒和第 1.5 秒两帧有差异），能跟鼠标的特效会跟鼠标。

## 已实现（细节见 `docs/M5-着色器翻译.md`）

- **特效**：WE 着色器在运行时翻译成 Metal（GLSL 路线，按报错补隐式类型转换），单通道、多通道、中间缓冲、
  遮罩与参数覆盖、鼠标位置；翻译结果有磁盘缓存；矩阵约定按 HLSL 语义（`mul(a, b)` → `b * a`）；
- **粒子**：CPU 模拟 + WE 自带的 genericparticle 着色器；球形/盒形发射器，寿命、大小、颜色、速度、旋转等初始化，
  运动、淡入淡出、闪烁、振荡、湍流、控制点吸引等算子；精灵图逐帧、拖尾、子系统（static / eventfollow）、
  跟随鼠标的控制点、折射粒子（雨打在玻璃上）；
- **木偶变形**：.mdl 网格、骨骼（MDLS）和动画（MDLA），按动画层在 CPU 上蒙皮；木偶图层上的特效；
- **合成**：合成层 / 全屏后处理层、`_rt_imageLayerComposite` 引用别的图层（含隐藏图层）、形状图层；
- **文字**：场景自带字体用 CoreText 排版，时钟等内容由脚本算出；
- **脚本**：属性脚本（位置、缩放、透明度、颜色、显隐）和文字脚本用 JavaScriptCore 求值，每次调用 50 毫秒执行时限；
- **声音**：场景声音对象（循环 / 随机间隔 / 单次，音量关键帧），菜单"播放壁纸声音"统一控制，默认静音；
- **资源**：贴图按屏幕上用到的分辨率加载，构建后把解码用过的内存还给系统。

## 靠推断、没有和 WE 核对过的地方

这些都写在代码注释里，一旦有 WE 的参照截图，应该优先核对：

- 粒子各组件缺省字段的默认值（WE 没有公开）；colorrandom 在两色之间插值；
  ~~ropetrail 用拉长的精灵近似~~ 2026-09-28 已改：rope / ropetrail 两种画法都按 WE 文档实现成带子
  （见下面"粒子画法"一节）。带子的两个参数仍是推断：uvscale 当成"整条带子上把贴图铺几次"、
  subdivision 当成切角的次数（默认 3，`~/wp` 里显式写过 0 和 3）；
- 形状图层默认 128×128（按 WE 自带光束预设反推）；光束画回画面时的混合方式（光线周围可能有暗边）；
- 属性关键帧的贝塞尔手柄单位；动画层 `offsetedStartAni` 的起始进度；
- 控制点覆盖值按系统自己的坐标（按 WE 自带预览场景推断）；
- 文字排版：只核对过单行、居中的写法；
- **文字图层的边界保护是产品决定，不是 WE 的行为**：WE 的文档说画布比例和屏幕不一致时连时钟一起切掉，
  我们只把文字框挪进屏幕上看得见的那块画布（其余画面照旧铺满）。挪多少、贴哪条边见
  `docs/M5-着色器翻译.md` 的"时钟被屏幕切掉"一节。
- ~~图层特效的缓冲空间~~ 2026-09-28 已改：图片/形状/文字的链子改在**合成（整屏）尺寸**的缓冲里算
  （WE 的 `_rt_*CompoBuffer` 就是整屏大小），图层画在自己的屏幕位置上、取回时按屏幕矩形采样。
  Lucy 的时钟因此和 WE 的 4K 截图一样清楚。木偶网格图层和合成层上的特效仍是图层尺寸（待跟进）；
  显存到 WE 的量级（4K 下 Lucy 约 600 MB），共用缓冲池还没做。还有一处小差异：把场景里存的
  `rayintensity = 2` 算进去时，时钟外比 WE 多一层很淡的光（用默认值 1 就一致）——
  WE 可能没应用这份工作坊特效的参数覆盖，原因待核对。见 `docs/M5-着色器翻译.md` 的
  "时钟上的辉光会把字糊掉"一节。
- **2026-09-29 修正：所有图层的特效都改回在图层自己的空间里算**（整屏合成空间整套撤掉，只有合成层 /
  全屏层仍从当前画面里取）。图片图层是第二步改的，原因见下面"X-ray 错位"；文字、形状、木偶是第一步：
  用户反馈 Lucy 的"时间模糊""人物上有个小方块挡着"，对照 WE 的 4K 截图查下来：
  - 小方块是"光束 - 角"（shape: quad + lightshafts，DIRECTDRAW）：光束的角点、羽化都按**图层的 0–1 纹理坐标**
    定义，放到整屏里算，射线铺满整屏、再被 512×512 的形状四边形切出硬边；改回形状自己的框以后在框里淡出，
    和 WE 一样只剩背后一点青色的光；
  - 时钟的"模糊"是 shine 的射线长度按**缓冲宽度的比例**算，整屏宽的缓冲里拖出约 150 像素、按 8 个采样点
    断续排开的横向残影。WE 的文字图层有 `padding`（这里是 32）专门给特效留边，说明特效在"框 + 留边"里算；
  - WE 截图里时钟字芯是纯白（255），可默认透明度是 0.66：说明 WE **先上色、再跑特效**（辉光的合成通道
    `albedo.a = saturate(albedo.a + rays.a)` 把透明度加回 1）。我们以前先跑特效、最后乘 0.66，字芯最亮 168；
  - macOS 的字体平滑会把笔画加粗，文字位图关掉平滑以后笔画接近 WE。
  - Lucy 头发右侧的几道灰色横条（WE 里没有、main 分支的渲染里也没有）：木偶的贴图是部件**图集**，部件在图集里的
    摆放和它在画面上的位置无关。链子搬进整屏缓冲后，图层框伸出屏幕的那部分图集被切掉——长发恰好在那里，
    网格只能取到屏幕边缘被拉长的像素。木偶的链子改回图集自己的空间、网格直接用图集 uv 以后，发丝恢复正常；
  - 时钟辉光的强度（**按 WE 截图校准，原因待查**）：场景存的 `rayintensity = 2` 画出来光晕把字撑胖；只把它换成 1、
    其余参数照旧，字芯占比 / 光晕占比和 WE 截图最接近（亮块的位置也一致，说明噪声参数是生效的）。
    用 WE 自己编译的着色器缓存（`~/wp/3521337568/shaders/blobsSM40`）核对过：射线通道只有"4 个方向 × 8 采样"和
    "3 个方向 × 15 采样"两种，和我们选的开关一致；翻译出的算术、缓冲格式、参数名也一致。比较可能的解释是我们
    用 CoreText 画的笔画比 WE 粗约 1.4 倍（辉光按笔画面积累加、合成时再平方）。经用户确认，文字图层上的辉光
    射线强度先乘 0.5（`textGlowCalibration`），以后把字形画得和 WE 一样细了再改回 1；左上角"光束 - 线性"在我们这里是一个小光锥（main 分支时就这样），
    WE 里那一片只是淡淡的雾光，也待核对。

## 验收之后补上的：系统音频律动（2026-09-28）

- **采集**：`DesktopHost/SystemAudioSpectrum` 用 Core Audio 的进程 tap（`CATapDescription` 的全局立体声 tap，
  macOS 14.2+）抓系统输出，挂到私有聚合设备上读样本；第一次用会弹一次"系统音频录制"授权，
  拿不到授权就按静音处理（界面照常，日志里写明原因）。
- **频谱**：1024 点 FFT → 20 Hz–16 kHz 的 16/32/64 段**对数**分频，按时间平滑。
- **接线**：特效的 `g_AudioSpectrum16/32/64Left|Right`（WE 的 AUDIOPROCESSING 通道）每帧刷新，
  含它们的链改为每帧重算；脚本的 `engine.registerAudioBuffers` 返回的 average / left / right 同样每帧刷新。
- **核对**：`WallpaperTool audio-spectrum [秒数]` 边放声音边打印 16 段频谱（本机实测峰值 0 → 0.63 → 衰减回 0）；
  2573849422（Bass Clock 24h）的缩放脚本随声音变化（相邻两帧差 1.6 万像素）。
- 还没做的：特效/脚本以外的音频用法（例如 WE 的 RGB 设备联动）没有涉及。
- **复查修正（2026-09-29）**：①交错立体声的左声道以前把 L/R 两路样本全塞进去做 FFT，右声道只有一半样本却按
  1024 点读（越界读）——改成按帧拆左右，非交错（每声道一个缓冲）也支持，有单元测试；②以前**每个场景**一载入就开
  系统录音，现在只有用到 `g_AudioSpectrum*` 或 `registerAudioBuffers` 的场景、而且在播放时才采集（引用计数，
  暂停 / 换壁纸就停）；③Info.plist 补上 `NSAudioCaptureUsageDescription`；④离线工具默认不采集（结果不随正在放的
  音乐变），`SYSTEM_AUDIO=1` 时才接上。

## 待核对：恰巴耶夫壁纸（2989540197）的"一闪一闪"（2026-09-28）

用户反馈这张壁纸的雪花"突然一闪一闪"。逐项查过：

- **雪花本体**：两张 "Rising debris" 系统都是 `animationmode: randomframe`（8 帧 debris 精灵图）+ angularmovement + alphafade。
  我们的 randomframe 是"每个粒子恒定选一帧"（lifeValue 固定），逐帧渲染 1/60 步长下相邻帧差异平滑，**没有**逐帧闪。
- **"闪光点 lighting spot"**：3 个大光斑（size 1000、blending translucent）挂着 **没有参数的 `oscillatesize`**，
  发射器只在前 3 秒工作。WE 编辑器的算子默认值没有公开，我们按"没写参数＝不改动"处理，

### 纯色图层（solidlayer）上的特效现在会画

现在纯色层也建特效链，链的输入是"1×1 白贴图 × 图层颜色"（颜色和透明度走和文字图层同一套 `colorIntoChain`，

- 特效总数 1294 → 1297（正好多出这三个）；
- 和改动前的渲染逐张比较，3147430778 / 3146803575 / 3169364633 三张的画面变了（2%–6% 的像素），

- 和 WE 预览图的差异：3147430778 8.8 → 5.2，3146803575 60.7 → 57.8，**没有一个场景变远**；
- 新增 `SolidLayerEffectTests`（自写夹具，不含 WE 内容）：特效确实在纯色层上跑、图层颜色和透明度是链的输入。

静音时 `Simple_Audio_Bars` 的 `TRANSPARENCY` 默认是 REPLACE（`alpha = bar * opacity`），所以柱子高度为 0、
什么也不画——这是对的；放音乐时才会出现柱子。

### 逗号分隔的向量值

WE 的向量除了空格分隔（`"1 0.5"`），还有逗号分隔的写法（`"0.0, 1.0"`，特效参数里很常见）。我们以前只按空格切，
`"0.0, 1.0"` 会被解析成 `[1.0]` 一个值，整个向量错位（`Simple_Audio_Bars` 的 `Lower/Upper Bar Bounds` 就踩到了，
柱子高度按 `mix(1, 0, volume)` 算成了反的）。现在 `SceneValue`、`ShaderInterface` 和粒子组件的数字列表都按
空格**或逗号**切分。全量回归里因此变化的场景都在预期范围内，且没有一个离 WE 预览更远。

### 回归基准工具：`WallpaperTool regress`

```bash
# 第一次：按屏幕尺寸在第 0 秒和第 5 秒各存一张基准
TARGET_WIDTH=3024 TARGET_HEIGHT=1964 swift run WallpaperTool regress ~/wp ~/wp-assets ~/wp-baseline
# 以后：和基准逐像素比较，只列出真正变了的场景
TARGET_WIDTH=3024 TARGET_HEIGHT=1964 swift run WallpaperTool regress ~/wp ~/wp-assets ~/wp-baseline
```

- 变更是有意的时候用 `REGRESS_UPDATE=1` 把这次结果写成新基准；
- 基准目录里记了尺寸（`size.txt`），尺寸不一致时直接停下、不动基准（`REGRESS_UPDATE=1` 按新尺寸重建）；
- 和桌面上一样按屏幕尺寸建渲染器、按同一尺寸出图；
- 阈值：平均差 > 0.5 或明显变化的像素 > 0.1% 就报出来；
- 返回码：有场景变了或有失败时为 1，全一致为 0，可以直接用在脚本里。

为什么不用"和预览图的差异"：那张图是 WE 编辑器出的缩略图，取景（裁切、缩放、动图取哪一帧）和实际渲染
不一定一致，动图还只读第一帧——这几次排查里它就误导过。基准比较只回答"这次改动有没有改变画面"。
（带实时时钟的场景每次都会算成变了，这是预期的。）

## 2026-09-29（续）：运行时建图层的可视化条真的画出来了

用户反馈"有些壁纸里的音乐可视化不出现"。语料里 30 个场景用到音频，其中 4 个是用
`thisScene.createLayer` 现建柱子的（2350484035 / 2255543849 / 2348181456 / 2475316820）。
定位下来是三个各自独立的问题，都不在"音频采集"上（`WallpaperTool audio-spectrum` 实测频谱跟着音乐在动）：

1. **脚本里的资源路径是作者打包前的本机路径**。2350484035 的脚本写 `createLayer('models/bar.json')`，
   包里实际是 `models/workshop/2115341179/bar.json`。`SceneFiles` 现在在原路径找不到时按
   "顶层目录 + 文件名"在子目录里再找一次（多个同名取路径最短、字典序最小的，保证结果稳定），
   找不到的话 63 根柱子一根都建不出来。
2. **只读音频频谱、不提时间或随机数的脚本被当成静态脚本**，只在构建时跑一次，
   柱子高度永远停在 0。`engine.registerAudioBuffers` 注册过的脚本现在强制每帧重算
   （音频本身就是每帧变化的输入），并且**音频频谱在脚本求值之前推给它**，当帧就能用到。
3. **脚本把 scale 设成 0 分量**（模板里是 `new Vec3(barWidth)`，y、z 都是 0）：
   世界矩阵要做逆变换（`delta` = 当前世界 × 构建时世界的逆），分量是 0 时矩阵不可逆、
   逆矩阵全是 NaN，图层直接画不出来。现在缩放分量取一个安全下限（`SceneState.safeScale`，
   保留符号，负缩放是合法的镜像），运行时图层建四边形时只烘平移和旋转
   （`SceneRenderer.withoutScale`），缩放留给每帧的 delta 施加——否则建图层那一刻的 0 缩放
   会永久烘进顶点，之后脚本再改 scale 也救不回来。

验证（离屏渲染，边放连续音边渲染，`SYSTEM_AUDIO=1`）：

- 新增 `RuntimeLayerDrawTests`（自写夹具，不含 WE 内容）：`createLayer` 建的图层会被画出来；
  建的时候高度为 0、之后每帧再改大，也要画得出来。

### 可视化条的位置

- **图层对齐（`alignment`）**：WE 的图层有对齐点（`center` / `top` / `bottom` / `left` / `right` 及组合），
  对齐点落在 origin 上。可视化脚本（2350484035、2475316820 用的是同一个工作坊脚本）在运行时把柱子设成
  `bar.alignment = 'bottom'`，柱子从 origin 往上长。原来不认对齐，柱子以 origin 为中心上下对称，下半截伸出屏幕底边。
  现在 scene.json 的 `alignment` 和脚本的 `layer.alignment` 都认：四边形在图层自身坐标（缩放之前）挪半个宽 / 高，
  缩放以对齐点为基准；图片、纯色、文字、形状、材质着色器、合成层、运行时建的图层都走同一个 `alignedWorld`。
  不认识的写法（包括英式拼法 `centre`）按居中。

### 场景泛光（general.bloom）

语料 351 个场景里 16 个开了场景泛光，原来一个都没画。WE 自带素材里有这几个着色器，按它们推出链的顺序（引擎里的渲染图不公开）：
`downsample_quarter_bloom`（整帧 → 1/4，四点平均后按阈值提亮、乘强度和色调）→ `downsample_eighth_blur_v`（→ 1/8，13 点横向高斯）
→ `blur_h_bloom`（1/8 上 13 点纵向高斯）→ `combine`（原画面 + 泛光）。两个模糊的采样间隔都是 `g_TexelSize × 8`，只有
`g_TexelSize` 取**整帧**像素尺寸、模糊画在 1/8 尺寸上时才正好一格一采样，所以四步都按整帧尺寸给 `g_TexelSize`。

- 只做非 HDR 场景（16 个里 14 个）。HDR 场景（`hdr: true`，2490106428、3142391697）的泛光是另一套：阈值 1、亮度超过 1 的部分才泛光、
  多级迭代，要浮点精度渲染。我们的画面是 8 位的，照搬会让本来就是纯白的地方（3142391697 背景的窗户）都泛光，所以先不画。
  **3142391697 的"光圈闪光"因此仍然没有效果**，要等 HDR 渲染。
- 新增测试：SceneBloomTests（夹具包里放同名的简化着色器，验证链路、强度参数、HDR 跳过、绑到用户属性的开关）。
