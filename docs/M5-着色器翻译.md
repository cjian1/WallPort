# M5 第一步：WE 着色器方言翻译（对照实验）

特效（24 个场景里用了 139 次）全都要用 WE 自己的着色器，所以 M5 先解决"把 WE 着色器变成 Metal"。

## 流水线（`Sources/ShaderTranslation`）

1. **读接口**（`ShaderInterface`）：从原始源码读出开关（`// [COMBO] {...}`）、材质参数（uniform 后面注释里带 `"material"` 的）、贴图槽（默认贴图、关联的开关）。这些都写在注释里，必须在预处理之前读；
2. **拼装**（`ShaderAssembler`）：`#version 450` + 方言宏（`texSample2D`、`mul`、`frac`、`saturate`、`lerp`、`CAST4`……）+ 开关的 `#define` + 展开 `#include`（每个头文件只展开一次）；
3. **预处理**：交给 glslang，只做预处理，把 `#if` 和宏全部展开；
4. **结构改写**（`GLSLRewriter`）：所有声明提到开头；`attribute`/`varying` 分配 location（两个阶段按名字共用一张表）；普通 uniform 收进一个 `layout(scalar)` 的 uniform 块；`g_TextureN` 绑定到 N + 1；`gl_FragColor` 换成输出变量；`int x = 浮点表达式;` 加 `int()`；
5. **编译**：glslang 编成 SPIR-V → SPIRV-Cross 转 Metal → Metal 编译并把两个阶段连成管线。

## 实验结果（2026-09-28，`~/wp` 的 24 个场景）

语料是场景里**实际用到的**全部着色器组合（着色器 + 材质和场景设置的开关 + 给了贴图的槽），去重后 53 个。

| 轮次 | 改了什么 | 完整通过 |
|---|---|---|
| 1 | 初版 | 8 / 53（15.1%） |
| 2 | 按任意换行符切行：WE 着色器用 Windows 的 CRLF，Swift 里 `\r\n` 是一个字符，按 `\n` 切不开，导致 `#include` 没被识别；`sample` 改名（GLSL 450 保留字） | 43 / 53（81.1%） |
| 3 | 去掉 `#require`；声明提到开头；`int` 初始化加 `int()` | **50 / 53（94.3%）** |

剩下 3 个都是 HLSL 允许、GLSL 不允许的隐式类型转换，各自只影响 1 个场景：

- `effects/shimmer`：把 vec4 传给参数是 vec2 的函数；
- `effects/cloudmotion`：把 vec4 赋值给 vec2；
- 一个创意工坊自制特效：把 float 赋值给 int（不是声明时的初始化）。

计划的解决办法：根据 glslang 报错的行号自动补上类型转换再重编（最多几轮）。

注意：94.3% 只说明"能编译、能连成管线"，不说明算出来的画面对。正确性要等特效真正渲染出来再验证。

## 结论：走 GLSL 路线

HLSL 路线（把方言改写成 HLSL，交给 glslang 的 HLSL 前端或 DXC）唯一明显的好处，是天然接受上面那类隐式转换，但只涉及 3 个组合；代价是要把整套声明写法改写成 HLSL 的结构，工作量大得多，还有矩阵构造顺序等语义差异的风险。本机也没有 DXC。所以继续走 GLSL 路线，剩下的类型问题用"按报错补转换"解决。

## 新发现

- **`#require LightingV1`** 引入的是 WE 引擎内部的函数库（`PerformLighting_V1` 等），不在任何素材文件里。只有打开 `LIGHTING` 等开关时才会用到（带光照的 3D 模型、木偶变形），到时候要自己实现；
- 特效材质的参数写在 uniform 注释里，场景里每个特效实例用 `constantshadervalues` 覆盖，用 `textures` 替换贴图，用 `combos` 改开关；
- 顶点着色器用 `mul(vec4(a_Position, 1.0), g_ModelViewProjectionMatrix)`（行向量 × 矩阵），上传矩阵时要转置；
- 音频响应的特效在顶点着色器里读 `g_AudioSpectrum16Left[16]` / `Right[16]`。

## 运行时接入的计划

- 运行时直接调用 glslang 的 C 接口（`glslang_c_interface.h`）和 SPIRV-Cross 的 C 接口（`spirv_cross_c.h`），不起子进程；翻译结果按"着色器 + 开关"缓存到磁盘；
- glslang（BSD-3 类）和 SPIRV-Cross（Apache-2.0）的源码随项目一起编译（`Vendor/`，见 `Vendor/README.md`），
  不依赖 Homebrew 或其它预装库。

# M5 第二步：运行时翻译与单通道特效（2026-09-28）

## 运行时翻译（`Sources/ShaderCompiler`）

- 进程内调用 glslang（C 接口）和 SPIRV-Cross（C 接口），不再起命令行子进程；
- uniform 块按 `layout(scalar)` 紧密排列，原生一侧按成员声明顺序算偏移（`UniformBlockLayout`），写值用 `UniformBuffer`；
- 端到端测试：手写一段方言着色器，完整翻译后用 Metal 画一帧再读回像素，一次核对 uniform 偏移、贴图绑定、两个阶段的 varying 对应、矩阵的行向量约定——第一次运行就通过；
- 源码编进项目后，之前链接 Homebrew 的 macOS 15 版库时的那堆警告也消失了。

## 特效链（`Sources/SceneRenderer/EffectChain.swift`）

- 带特效的图层：先把贴图拷进和图像同尺寸的离屏纹理（去掉补齐边距），再依次经过每个特效通道，两张纹理轮流做输入输出，结果当作图层贴图画到屏幕上；
- 每个通道：`g_Texture0` 为上一步结果；其他贴图槽按"场景覆盖 → 材质 → 着色器注释的默认贴图"取；材质参数按"场景的 constantshadervalues → 材质 → 默认值"取；
- 内置 uniform：矩阵（单位矩阵）、`g_Time`、`g_TextureNResolution`（纹理尺寸, 图像尺寸）、`g_TexelSize`、`g_PointerPosition`（暂时固定在中心）、`g_Daytime` 等；
- 按"着色器 + 开关 + 有贴图的槽"缓存编译结果；
- 有特效的场景用 CADisplayLink 按每秒 30 帧渲染，被遮挡 1 秒后或手动暂停时停下，场景时间也停住。

## 结果（`~/wp` 的 24 个场景）

| 项目 | 结果 |
|---|---|
| 渲染的特效 | 75 个（挂在隐藏图层、木偶变形图层、文字等非图片图层上的不计） |
| 画面随时间变化 | 带特效的 15 个场景里 13 个；另外 2 个经诊断都是正确行为：一个的 waterflow 没画流向图（用默认的"无流动"），一个的 xray 跟鼠标位置有关、和时间无关 |
| 翻译失败 | 2 个（shimmer、cloudmotion，隐式类型转换） |
| 多通道特效（暂不支持） | shine 5 个 |
| 桌面运行 | Lucy 场景 2 个特效：CPU 5.2%、内存 244 MB；20 个特效的场景：CPU 8.8%、内存 538 MB |

## 已知问题与下一步

- 内存：每个带特效的图层要两张和原图同尺寸的缓冲，大图很占内存；应按图层在屏幕上的实际像素限制缓冲尺寸；
- 多通道特效（shine、blurprecise）：按 effect.json 里的 fbos / bind / target 调度中间缓冲；
- 隐式类型转换的 2 个着色器：按编译报错补转换；
- 鼠标位置、音频频谱还没接入（xray、音频响应类特效需要）；
- 翻译结果还没有缓存到磁盘，每次启动都要重新翻译（场景构建 0.3–1.6 秒）。

# M5 第三步：多通道特效、隐式转换、缓冲尺寸（2026-09-28）

## 多通道特效

effect.json 的结构（用 shine 核对）：`fbos` 声明本特效的中间缓冲（`scale` 为分辨率除数）；每个通道有 `material`、可选的 `target`（画到哪个缓冲，不写就是特效输出）和 `bind`（把 `previous` 或某个缓冲接到 `g_Texture{index}`）。场景里特效实例的 `passes[]` 按顺序覆盖各通道。

特效链改为"特效 → 通道"两层：每个特效有自己的中间缓冲，特效之间仍用两张主缓冲交接。shine 的五个通道（降采样 → 投射 → 横向模糊 → 纵向模糊 → 合成）全部按定义接通。

## 隐式类型转换（`ImplicitConversionFixer`）

编译失败时按 glslang 的报错补转换再试（最多 4 轮），只改出错的那一行：

- 赋值两边类型不同（vec4 → vec2、float → int）：右边包上目标类型的构造函数；`for (int i = 浮点; …)` 只改初始化部分；
- 用户函数找不到匹配的重载：按源码里的函数定义给每个参数包上类型；
- 内置函数找不到匹配的重载（如 `max(0, v)`）：整数字面量改成浮点，max/min 的字面量参数挪到后面；
- 片段着色器的 varying 比顶点输出的少分量（D3D 允许，Metal 不允许）：按顶点的类型接收、换名，在 main 开头截断赋值；片段读了顶点没有输出的 varying 时改成值为 0 的变量。

结果：场景里用到的 53 个着色器组合 **53 / 53（100%）** 编译并连成 Metal 管线；24 个场景渲染出 82 个特效，翻译失败为 0。

## 特效缓冲尺寸

构建场景时传入屏幕像素尺寸，特效缓冲不超过图层在屏幕上实际占的像素（只缩小不放大）。20 个特效的场景内存 538 → 473 MB，效果有限：大头是和原图同尺寸的遮罩贴图，留待统一优化。

## 还没做的

- 内存：遮罩等贴图按缓冲尺寸缩小、纹理改用 GPU 专用存储；
- 鼠标位置、音频频谱；
- 翻译结果缓存到磁盘；
- 场景里还不支持的内容：粒子 38、脚本驱动的字段 21、文字 13、非图片图层上的特效 6、合成层 2、形状 2、木偶变形 1。

# M5 第四步：翻译缓存、鼠标位置、内存分析（2026-09-28）

## 翻译结果的磁盘缓存

以"两个阶段拼装后的源码 + 翻译器版本"的 SHA-256 为键，把 Metal 源码、uniform 布局、接口信息存成 JSON（`~/Library/Caches/MacWallpaper/Shaders`）。拼装只是字符串处理，命中时跳过预处理、编译和转换；缓存文件损坏时自动重新翻译。

效果有限：20 个特效的场景构建 1.43 → 1.35 秒。这个场景只有 4 个不同的着色器组合，主要耗时在解码大图、解压遮罩和上传纹理。构建在后台线程进行，不影响菜单栏。

## 鼠标位置

- `g_PointerPosition`：鼠标在当前屏幕上的位置，0–1，**原点在左上角**（xray 着色器里写着 `pointer.y = 1.0 - pointer.y; // Flip pointer screen space Y to match texture space Y`）；每帧更新，鼠标在别的屏幕上时保持最后的位置；
- `g_EffectTextureProjectionMatrix`（及其逆矩阵）：图层自身坐标（-1…1）→ 屏幕裁剪坐标，按图层的真实位置、大小和屏幕投影计算；
- 验证：xray 场景在鼠标位于左右两处时的画面差异从 0.00 变为 0.60。

## 内存去向（20 个特效的场景，共 430 MB）

| 类别 | 大小 | 实际是什么 |
|---|---|---|
| 显存（共享） | 169 MB | 图层贴图，以及与原图同尺寸的遮罩（每个特效一张） |
| 显存（GPU 专用） | 84 MB | 特效缓冲 |
| IOSurface | 69 MB | 屏幕绘制的三重缓冲（每张 3024×1964） |
| 堆内存 | 75 MB | 解码、编译过程中的临时数据等 |

优化方向：遮罩按特效缓冲尺寸缩小（约省 60%）；动画场景的绘制缓冲从 3 张减到 2 张。普通场景在 240 MB 左右，暂不处理。

# 木偶变形：按网格静态拼装（2026-09-28）

Lucy 场景的主角用的是木偶变形模型：图层贴图是身体部件拼成的图集，模型文件 `Lucy_puppet.mdl` 里的网格把部件拼成完整的人物。M4 起一直跳过这类图层（直接画图集是一堆零件），所以 Lucy 不出现。

## .mdl 的结构（MDLV0023，目前只有这一个样本，逐字节核对）

| 位置 | 内容 |
|---|---|
| 开头 | `MDLV0023` NUL，3 个整数（0x01800009、1、1），材质路径 NUL，一段 0 字节 |
| 顶点区 | 顶点格式 0x0180000F，字节数，每个顶点 80 字节：位置 3f、法线 3f（都是 0,0,1）、切线 4f、4 个骨骼编号（u32）、4 个骨骼权重、纹理坐标 2f |
| 索引区 | 字节数，u16 索引，三个一组（Lucy：2589 个顶点，4523 个三角形） |
| 摊开位置 | 每个顶点在图集上的位置（3f）：第一个顶点是 (235.5, 966)，正好等于 ((u−0.5)×图像宽, (0.5−v)×图像高)；给编辑器用 |
| 之后 | `MDLS`（骨骼，Lucy 有 61 根，根骨骼在 (−803, −404)）、`MDLA`（动画，约 1.2 MB）、`MDLE` |

顶点位置是拼装好的姿势，坐标以图层原点为中心、y 向上、单位是画布像素，不局限在图层矩形之内。Lucy 的网格整个在图层原点的左边，放到画布上正好站在画面中央、脚踩底边，和预览图的构图一致。

## 现状

- 按网格静态绘制，纹理坐标乘补齐比例；和预览图的差异从 48.2 降到 34.1，人工看过，拼装正确；
- 骨骼动画见下一节；木偶图层上的特效见"合成层"一节。

## 骨骼动画（2026-09-28）

### MDLS / MDLA 的结构（同一个样本逐字节核对，解析结束位置与段头记录的结束偏移完全吻合）

| 段 | 内容 |
|---|---|
| `MDLS0004` | [段结束的绝对偏移][骨骼数 61]；每根骨骼：名字 NUL（Lucy 的都为空）、标志、父骨骼编号（根为 −1，父骨骼总在前面）、矩阵字节数 64、相对父骨骼的局部矩阵（列主序）、编辑器用的 JSON NUL。之后到段结束还有约 5 KB 每骨骼的附加数据（编辑器用，未解析） |
| `MDLA0006` | [段结束的绝对偏移][动画数 5]；每个动画：编号（就是场景 animationlayers 里的 animation）、4 字节未知、名字、播放方式（loop / single）、帧率、帧数、4 字节未知、骨骼数；每根骨骼：4 字节未知、字节数、(帧数 + 1) 帧 × 36 字节（平移 3f、欧拉角 3f 弧度、缩放 3f）；动画结尾 35 个 0 字节 |

动画帧是骨骼的完整局部姿势（第 0 帧与绑定姿势一致），不是增量。顶点位置就在绑定姿势的模型坐标里：
每组顶点的中心离它主要绑定的骨骼中位数 52 像素；只动根骨骼时所有顶点整体平移（用独立的 Python 实现核对过）。

### 播放

- 场景对象的 `animationlayers[]`：animation（动画编号）、blend、rate、additive、visible；
- additive 层把"动画姿势 − 绑定姿势"乘权重加上去；非 additive 层按权重覆盖；
- loop 循环，single 播一遍停在最后一帧；帧之间线性插值，角度取最短方向；
- CPU 蒙皮（2589 个顶点 × 4 个权重），每帧写进三个轮流用的顶点缓冲。

Lucy 的 5 层动画：4 层循环的小动作（头发、衣角，最大转角 0.9 弧度），1 层 single 的入场动画
（根骨骼从右下方滑到原位、缩放从 0.8 到 1；12 fps、60 帧，5 秒）。人工看过入场和循环帧，网格没有撕裂。
CPU：Lucy 整个场景（粒子 + 骨骼动画）release 构建 5.1%。

### 错开起点的脚本（2026-09-28）

Lucy 的头发、衣角三层在 `animationlayers[].visible` 上挂了脚本，想让这几层循环不要同步。函数本身
定义在场景自己的内联脚本里（`shared` 不是引擎内置的命名空间，按官方文档它只是"给多个脚本共享数据的空对象"）：

```js
function offsetedStartAni(ani, percentage = 1) {
    ani.play()
    ani.setFrame(ani.frameCount * percentage)   // 官方文档：frameCount 是动画总帧数，setFrame 设当前帧
}
```

所以语义就是"从动画的 `percentage` 处开始播"：Lucy 的三层分别取 0.4 / 0.35 / 0.3，即 2.5 秒循环里错开
1.0 / 0.875 / 0.75 秒。滑块默认值是 1，对循环动画等于没偏移（多走一整圈），所以没动过这个值的场景不受影响。

我们不做脚本引擎，只认出这一种写法（`visible` 的脚本里出现 `offsetedStartAni` 且带 `scriptproperties.percentage`），
把它换算成该层动画的起始时间偏移（`AnimationLayer.startProgress` → `PuppetAnimator.Layer.startOffset`）。
其它脚本仍然不执行。

# 粒子系统（2026-09-28）

## 做法

- **格式**（`WallpaperFormats`）：`ParticleDefinition` 读粒子定义 JSON，组件统一存成"名字 + 数值字段 + 字符串字段"，
  缺省字段在使用处给默认值；`SceneDescription.Object.particleOverride` 读场景里的 instanceoverride；
  `TexFile.spriteSheet` 读精灵图段（TEXS0002 无帧宽高头、TEXS0003 有，帧记录 32 字节）。
- **模拟**（`ParticleSimulation`，CPU）：发射器 sphererandom / boxrandom；初始化 lifetime / size / alpha / color /
  hsvcolor / velocity / rotation / angularvelocity / turbulentvelocity；算子 movement / angularmovement / alphafade /
  alphachange / sizechange / oscillatealpha / oscillateposition / turbulence / controlpointattract。
  随机数可复现（同一种子得到同样的粒子）。starttime 在载入时预模拟，步长不超过 1/30 秒，最多 900 步。
- **绘制**（`ParticleLayer`）：直接用 WE 自己的 genericparticle 着色器（经 GLSL 路线翻译），
  每个粒子四个顶点，走着色器里"没有几何着色器"的那条路径；精灵图、拖尾、R8/RG88 贴图换算、材质的 overbright
  都由着色器自己处理。粒子的 z 在投影前压平，正交画面里不会被裁掉。
- **子系统**：static（含没写类型的）作为独立系统；eventfollow 在每个新出生的父粒子上发射并跟随它（流星的光晕）。
- **控制点**：flags 第 0 位跟随鼠标；场景覆盖的坐标是系统自己的坐标（未缩放），见 `ParticleLayer.controlPoints`。

## 从文档确认的语义（docs.wallpaperengine.io）

- alphafade：fadeintime 是"淡入完成的时刻"，fadeouttime 是"开始淡出的时刻"，都按寿命比例；
- sizechange / alphachange：starttime 之前是 startvalue，到 endtime 变成 endvalue；
- 振荡类：频率是"每一生振荡几次"；速度要有 movement 才生效，角速度要有 angularmovement；
- instanceoverride：count 是发射率倍数，rate 是模拟速度倍数，speed 同时作用于初速度和各种力。
  颜色倍数新版字段是 colorn（0–1），2018 年前后的场景写 color（0–255，例如 "255 165 0"）——两个都认。

2026-10-01 补的两处：
- **粒子系统的 x、y 转角**：系统按 Rz·Ry·Rx 立体地转，精灵的四个角也在系统坐标里算（g_OrientationRight/Up/Forward
  是世界坐标的轴：WE 的 genericropeparticle.vert 要先乘 g_ModelMatrixInverse 才把 g_OrientationForward 换到系统
  坐标里），所以转成侧面朝前的系统每个粒子都压成一条线、整个看不见。以前只认 z 转角，1457591167 的 Snow storm
  （x 转 90°、y 转 270°）画成了铺满屏幕的雾。本机库里用到 x、y 转角的只有 4 个粒子系统；图层仍只认 z 转角。
- **特效通道的顶点坐标**：画到特效输出的通道，a_Position 是图层像素（中心为原点、y 朝上），乘
  g_ModelViewProjectionMatrix 变成裁剪坐标；画到中间缓冲（有 target、老格式的 compose）的通道是裁剪坐标的四边形——
  WE 自带的这类通道直接写 `gl_Position = vec4(a_Position, 1.0)`。依据：植物摇摆 / 倾斜 / 透视的 Vertex 模式都按
  像素挪顶点（倾斜用 `g_Texture0Resolution.zw * g_TextureReductionScale`）。以前四边形一律是裁剪坐标，
  老版植物摇摆挪 3–10 像素变成挪几个画面宽，整张图大幅摆动（1446650543、1732032524）。不读这个矩阵的着色器
  照旧给裁剪坐标。老格式的 `"compose": true` 通道现在画进单独的缓冲、下一个通道的 previous 读它。
- **全面检查（2026-10-01，`WallpaperTool scene-report`）**：本机 329 个场景全部能建；特效用到的引擎 uniform
  只差 g_LayerModelMatrix（工作坊 rounded_mask 拿它算图层缩放，已补）；宏换了内容重定义按 HLSL 的规矩后面的生效
  （3795078488 的音频特效以前整个编不过）；脚本补了 WE 媒体集成的 MediaPlaybackEvent 等名字。剩下的：
  6 个场景的时钟图层把"拖动位置"脚本挂在了 visible 上（WE 里同样报错、同样按静态值），1 个粒子子系统 eventspawn、
  1 个粒子算子 vortex_v2 没做；场景的镜头视差（cameraparallax，17 个场景）、镜头抖动（3 个）、general.zoom（5 个）
  还没做——WE 没公开公式，参考实现（linux-wallpaperengine）的写法和 WE 文档对"延迟"的说法对不上，先不猜。
  **（2026-10-06 更新，M6）**：镜头视差、镜头抖动、`general.zoom` 和场景级重力 / 风都做了
  （幅度是保守推断值），并加了"特性覆盖检查"，把这类以前**静默忽略**的整场景特性报出来；
  本机 329 个场景的验收结果、判定口径和剩下的缺口见 `docs/M6-验收清单.md`。
- **applyUserProperties**：WE 在壁纸载入时用全部用户属性（原值）调一次脚本的 `applyUserProperties`，之后只传改了的。
  以前宿主从没调过：只在那里赋值的脚本拿到 undefined。2248783434（Morrigan & Lilith）的人物位置就是
  `new Vec3(originX, originY, z)`，originX/Y 只在 applyUserProperties 里赋值，结果人物跑到画布左下角。
  现在载入时调一次（我们改属性会重建场景，所以不用再传"改了的"）。本机 8 个场景的脚本有它，画面变了的只有这一个。
- **取景自检（`WallpaperTool framing-check`）**：按屏幕尺寸渲染的和按画布比例渲染后取中间的比，329 个场景里
  差得多的只有 3 个有"空边取景"的（预期）；其余是粒子、光晕重采样的小差别，没有"只显示一角"的。

WE 没有公开各字段的默认值，缺省值都是推断的（写在 `ParticleSimulation` 的解析处）；真实文件里多数字段是写全的，
推断主要影响 rotationrandom（41 个里 34 个没写 max）、colorrandom 的 max（58 个里 30 个没写）和 alphafade 的缺省时刻。

## 折射粒子（2026-09-28）

雨打在玻璃上：粒子按屏幕坐标去读"到这里为止的画面"，用法线图把取样位置挪一点，看起来就是隔着水珠看背景。

- 开关是 `REFRACT`，片段着色器用 `g_Texture3`（默认贴图 `_rt_FullFrameBuffer`，到这里为止的画面）、
  法线图在 `g_Texture1`（有贴图时自动打开 `NORMALMAP`），折射量是 `g_RefractAmount`
  ——它声明在 `common_particles.h` 里，所以读接口时要连 `#include` 的头文件一起扫（`ShaderInterface` 现在读拼装后的源码）；
- **屏幕坐标的方向**：WE 的 GLSL 路径里 `coord = xy / w * 0.5 + 0.5`，v = 0 在画面**底部**（HLSL 路径才翻 y），
  而 Metal 的纹理第 0 行在顶部。所以给折射粒子的那份画面拷贝要上下翻过来再绑（`FrameCopy.flippedCopy`），
  否则雨滴里的背景是上下镜像的；
- 画面拷贝和合成层一样，在屏幕这一遍中间结束编码、拷一份、再接着画：粒子画到哪儿，读到的就是那一刻的画面；
- 材质里的贴图现在按槽位全部取（0 号反照率、1 号法线图），着色器要用而材质没给的槽绑 1×1 黑色；
- 核对：`~/wp` 里 5 个折射材质、7 个雨滴系统全部渲染。3576135309 的"雨滴屏幕 4k"能看到玻璃上的水珠折射
  （人工放大核对）；3538825305 的 `rainperspective` 是"远处的雨"（尺寸 5、透明度 ≤ 0.3、速度 3000 的拖尾），
  画面上只有约 0.2% 的像素被轻微改动，是这层雨本来就该有的强度。

# 合成层、图层引用、形状图层，以及 mul 的矩阵约定（2026-09-28）

## 木偶图层上的特效

特效作用在贴图（身体部件图集）上，而不是拼装后的画面：Lucy 的几张遮罩（1185×1080，图层尺寸的一半）
有大片涂抹落在图层右侧 58% 的区域（例如一张水波遮罩 64% 的涂抹在 u > 0.7），而拼装后的网格根本不覆盖那里。
所以和图片图层一样，图集先经过特效链，再用网格画特效链的结果。Lucy 的 6 个特效（抖动、3 个水波、透明度、
光芒）都接上了，头发边缘出现和预览图一致的青色轮廓光。

## 合成层与全屏后处理层

WE 自带的 `composelayer` 着色器从 `_rt_FullFrameBuffer`（到这里为止的画面）里按图层四边形在屏幕上的位置取样，
填满图层自己的缓冲；`fullscreenlayer` 用 `passthrough` 取整个画面。实现：屏幕这一遍画到合成层时先结束，
把目标拷一份，特效链的第 0 步按图层四个角在屏幕上的位置取样（`EffectChain.sourceCorners`），跑完特效后
接着画（loadAction = load），结果按半透明混合画回原位。

## 图层引用 `_rt_imageLayerComposite_<编号>_a`

特效可以把别的图层（连同它自己的特效）的结果当贴图用，被引用的图层即使 `visible: false` 也要照算。
Lucy 的地球就是这样：地球贴图、夜面、云层、昼夜遮罩、星球遮罩都是隐藏图层，地球贴图自己带平移滚动（让地球转），
合成层先用黑色盖掉背景，再用 4 个 blend 特效混入它们，经 transform 和 fisheye 变成球面，最后用星球遮罩抠成圆形。

- 构建前先扫描所有特效覆盖里引用的图层编号；被引用的图层（可见或隐藏）都建一条特效链，没有特效的建一条
  只拷贝的链（去掉补齐边距，别的特效按 0–1 取样才对得上）；
- 被引用的图层结果长边限制在 2048：它们是被取样的贴图，按自己在屏幕上的尺寸算会偏大
  （Lucy 的 4000×2000 地球贴图按自身变换要 3819×1910，而合成层只按约 950 像素取样）；
- 没有时间、鼠标输入且输入固定的特效链只算一次（`EffectChain.isStatic`）。

## 形状图层

`shape: "quad"` 没有贴图，特效在一块透明的区域上直接画（光束特效的 DIRECTDRAW）。没写尺寸时按 128×128：
WE 自带的光束预设场景画布 256×256、形状缩放约 2.04–2.09，刚好铺满。没有特效的形状暂时不画。

## mul 的矩阵约定（修正）

WE 的着色器按 HLSL 习惯写矩阵：`m[i][j]` 是第 i 行、`mat3(…)` 按行填、`mul(v, M)` 是行向量 × 矩阵。
同样的源码在 GLSL 里下标和构造都按列，得到的是 HLSL 那个矩阵的转置，所以 `mul(a, b)` 必须映射成 `b * a`，
uniform 矩阵照常按列主序上传。之前映射成 `a * b` 再把 uniform 矩阵转置上传：uniform 矩阵结果对，
但着色器里自己构造的矩阵全被转置了——光束特效的 `squareToQuad` 算错导致什么都画不出来，粒子的旋转方向也反了。
WE 自带的 `common_perspective.h` 只在 HLSL 分支里自己实现 `inverse`，GLSL 分支用内置的，印证了这种理解。
修正后 24 个场景里 3 个和预览图更接近，没有变差的；新增测试锁住这个约定。

# 属性脚本：图层的位置、缩放、显隐（2026-09-28）

WE 的每个属性都可以挂脚本。`~/wp` 里除文字之外还有 16 处：`visible` 9 处、`origin` 5 处、`scale` 1 处
（有的对象同时挂多个）。

## 怎么跑

- 用同一个 JavaScriptCore 宿主（`SceneScript`）：`createScriptProperties` 属性构造器、`scriptProperties`、
  `thisLayer`（origin / scale / size / text / name）、`thisObject` / `thisScene` 的最小替身、
  `engine`（canvasSize / runtime / frametime / userProperties / isRunningInEditor）、`Vec3`（常见的向量运算）、
  `shared`、`localStorage`、`console`。`engine.runtime` 是"壁纸已运行的秒数"、`frametime` 是上一帧的时长，
  和官方文档一致；
- 构建时先算一遍，结果直接当静态值用（`81c327` 那种"位置 = 滑块 × 画布尺寸"的脚本就是这样生效的）；
- 脚本里出现 `engine.runtime`、`engine.frametime`、`Math.random`、`Date` 时按每帧重算——`~/wp` 里
  吊瓶的 `origin` 就是 `992.82 + sin(engine.runtime) * 10`，桌面上的吊瓶会轻轻上下浮动。
  每帧重算后把"构建时的变换 → 当前变换"的增量乘在投影矩阵前面（`ScriptedLayer.movement`），
  四边形、木偶网格、文字都跟着动；粒子系统和合成层还不跟脚本动；
- 每次求值都把当前的 origin / scale 和已运行秒数喂回脚本；脚本的返回值会喂给下一次（WE 的约定）；
- `init(value)` 的返回值是属性的初始值，`update` 从它开始算；没有 `update` 时就用它
  （Lucy 时钟的拖拽脚本只有 `init` 和几个 cursor 回调）。

## 跑不了的

- 单次调用超过执行时限（50 毫秒）被终止、从此停用的；
- 拿不到运行环境、算不出值的框架级脚本，例如 `16d063` 那个幻灯片控制器：它要靠
  `thisObject.getChildren()` 拿到所有子图层再逐帧改它们的 alpha / scale，我们只给了空列表，它自己就退出了；
- 把脚本挂错属性的：`~/wp` 里有 6 处把拖拽脚本（Vec3）挂在 `visible`（布尔）上，严格模式下
  `value.x = …` 会抛 `TypeError`——WE 里同样跑不出结果，所以两边都是"保持静态值"。

这些都会记进 `unsupported`：**"脚本驱动的字段（按静态值处理）"从 21 处降到 10 处**（6 个挂错字段的 +
3 个幻灯片 + 1 个调度器），并附上具体原因。剩下的 10 处都是真的跑不了，不是被漏掉。

## 结果（`~/wp` 的 24 个场景）

- `3521337568`：吊瓶按 `sin(engine.runtime)` 上下浮动（单独渲染两帧对比过，位移和公式一致）；
  "定位/positioning/x,y" 从编辑器的 (1920, 1080) 挪到脚本算出的 (-2035, 0)；
  Lucy 时钟的拖拽/悬浮脚本保持默认状态（桌面窗口不接收鼠标事件）；
- 24 个场景仍然 24/24、0 失败；
- 还没处理的组合：脚本移动的父图层带不动子图层（`~/wp` 里没有这种）；
  动态图层的特效链用的是构建时的投影矩阵（只有 xray 这类跟随鼠标的特效会受影响）。

# 文字图层与时钟（2026-09-28）

## 格式

文字图层就是一串字段，字体是真正的字体文件（不是字形图集）：

| 字段 | 含义 |
|---|---|
| `text` | 文字内容。可以直接是字符串，也可以是 `{"script": …, "scriptproperties": …, "value": …}`：`value` 只是编辑器里的预览值，真正的文字由脚本 `update(value)` 算出来 |
| `font` | `fonts/….ttf` / `.otf`，包内或 WE 自带素材目录里 |
| `pointsize` | 字号，和 `size`、画布坐标同一套单位 |
| `size` | 文字框；文字在框里按 `horizontalalign` / `verticalalign` 居中（`~/wp` 里 13 个文字对象都是居中、单行） |
| `color` / `alpha` | 图层颜色和透明度 |

`~/wp` 的 13 个文字对象、8 段脚本（`3521337568` Lucy 的时钟、`3535216365` 的 Date/Clock、
`3550149640` 的三层、`3560362683` 的 Time & Date、6 个场景里默认隐藏的"时间"）都按上面这套字段核对过。

**尺寸的理解**：文字按 `pointsize × 图层缩放` 画进 `size × 图层缩放` 的框里，居中摆放。
证据：Lucy 的框 427×199、字号 16（时钟在 3840 宽的画布上很小，符合它在场景里当装饰的定位）；
`3550149640` 的三层字号 26/36/37、缩放 1.14/0.28/0.25，画出来正好是"MONDAY"大、"28 SEP 2026"和"12:46"小，
和预览图里那块的构图一致。WE 没有公开这几个字段的单位，这里是按 13 个对象的比例关系推断的。

## 画法

- 用系统的 CoreText 把文字画成一张"白字 + 覆盖度 alpha"的图（非预乘，和 WE 的贴图一致），上传成贴图，
  再当普通图层画到框的位置上；颜色和透明度交给图层自己的 `color` / `alpha`，和 WE 的分工一样；
- 文字图层上的特效和图片图层走同一条路：先在离屏纹理上把特效链跑完，再画到框里。时钟的文字会变，
  所以这种链每一帧都重算，输入跟着当前那张文字贴图换；
- 贴图按"画布单位 → 屏幕像素 × 图层缩放"的分辨率画，最大边长 4096；
- 时钟：最多每秒问一次脚本，字符串变了才重画贴图、重新上传。有这种文字的场景要持续渲染
  （`SceneRenderer.needsAnimation` 里算了进去），CPU 上就是每秒一次几十像素的位图；
- 多行文本按 `\n` 分行，逐行摆；`maxrows` / `limitwidth` / 省略号这些还没处理。

## 脚本的最小宿主（`SceneScript`）

13 个文字对象的 8 段脚本只用到 `createScriptProperties()` 构造属性、`new Date()` 和字符串处理，
所以就给了个刚好够用的 JavaScriptCore 宿主：属性构造器（`addCheckbox` / `addText` / `addCombo` / `addSlider`，
`addCombo` 的默认值取第一个选项）、`scriptProperties`、`thisLayer`、`engine`、`shared`、`localStorage`。

- 脚本是 ES 模块（`export function update`），去掉行首的 `export` 就能当普通脚本跑；
- 场景里的用户属性会覆盖脚本声明的默认值；`scriptproperties` 里的值本身还可能套一层
  `{"user": …, "value": …}`，先解开再交给脚本，否则 12/24 小时制这类开关会读成"真"；
- 文字有两种写法：`update(value)` 返回新字符串，或者直接写 `thisLayer.text`（`3535216365` 的 Clock 就是），
  两种都支持；
- **不可信代码的边界**：脚本来自下载来的壁纸。JavaScriptCore 的 `JSContext` 本身不提供文件、网络、进程接口，
  脚本只能做纯计算；卡死靠**执行时限**防：所有脚本共用一个虚拟机，每次调用（载入、init、update）上限 50 毫秒
  （`JSContextGroupSetExecutionTimeLimit`，JavaScriptCore 导出但不在公开头文件里，按符号名查找），
  超时的调用被终止，这个脚本从此停用、退回静态值。最初的做法是静态检查（拒绝 `for` / `while` / `eval` 等），
  但它挡不住刻意绕过的写法（`(()=>{}).constructor("wh" + "ile(1){}")()`、灾难性回溯的正则），
  又会误伤带正常循环的脚本，现在只在取不到时限接口时才用它；
- 脚本抛异常时同样退回静态文字，并记进 `unsupported` / `problems`，不静默丢弃。

## 结果（`~/wp` 的 24 个场景）

- "文字 13" 从不支持清单里消失，24 个场景全部渲染成功；
- Lucy 从 19 层变 20 层，时钟显示"12:48 pm / 2026/09/28"（脚本按用户属性取了 12 小时制 + 年/月/日）；
- `3535216365` "+2 层"（Date/Clock）、`3550149640` "+3 层"（MONDAY / 28 SEP 2026 / 12:46）、
  `3560362683` "+1 层"（彩色分段字体，时间 + 日期）；
- 文字图层上的特效也接上了（Lucy 时钟的 shine 等 4 个），"非图片图层上的特效"从不支持清单里消失，
  全部场景渲染的特效 105 → 109；
- 6 个"时间"层是默认隐藏、由用户属性控制的，没开就不画（和其它隐藏图层一致）。

# 内存优化：按屏幕尺寸加载贴图、归还构建时的内存、两张绘制缓冲（2026-09-28）

`footprint` 看 Lucy 场景（桌面 3024×1964）的 600 MB：显存约 388 MB，大块堆内存 104 MB（其中 61 MB 是构建时解码贴图用过、
已经释放但分配器还留着的），画面缓冲（IOSurface）46 MB。场景包是内存映射打开的，不占这些。

- **贴图只加载屏幕上用得到的分辨率**（`TextureLoader.texture(named:fitting:)`）：图层贴图按它在屏幕上占的像素，
  被别的特效引用的隐藏图层按它结果的尺寸（长边 ≤ 2048）。原始格式从仍然够大的那层 mipmap 开始上传，
  内嵌 PNG/JPEG 直接按这个尺寸解码；补齐比例和图像尺寸不变。同一张贴图后来要更大的尺寸时重新加载。
  Lucy 的 4000×2000 地球原图从 42.8 MB 降到 10.8 MB，画面上只有地球区域 0.07% 的像素有细微差别；
  几个场景的构建时间也缩短了（例如 0.21 → 0.08 秒）；
- **构建完把释放的内存还给系统**（`malloc_zone_pressure_relief`）；
- **绘制缓冲从 3 张减到 2 张**：按 30 帧画足够，采样看 `nextDrawable` 只占渲染时间的约 5%，没有卡顿。

结果（桌面上，release 构建）：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| Lucy（3521337568） | 641 MB，CPU 15.1% | 568 MB，CPU 14.9% |
| 3550149640 | 485 MB | 427 MB |
| 3535216365 | 388 MB | 348 MB |

24 个场景和预览图的差异都在 0.1 以内（正常波动）。

没做的：特效链第 0 步的拷贝在"输入没有补齐边距、尺寸和缓冲一样"时可以省掉，但 Lucy 的链大多不满足
（图集有补齐边距；合成层按屏幕位置取样；3024×1964 的屏幕不是 16:9，全屏层的缓冲按画布算、和屏幕对不上），
收益太小，先不做。CPU 的大头仍是每帧五十来个特效通道的编码开销。

# 文字字号、壁纸库（2026-09-28）

## 文字字号的单位

用户反馈时钟字太小、调不了大小。原因是字号单位理解错了：WE 的 pointsize 是 300 DPI 下的磅值，
1 磅 = 300 / 72 ≈ 4.17 个画布单位。~/wp 里 13 个文字对象，按各自字体和字号量出的文字和作者的文字框之比
都集中在 4.17（"时间"那组框 375×165、文字 90×40，正好 4.1667），宽高一致。以前直接把字号当画布单位，
所有文字都小了 4 倍多；设置面板里的"大小"其实绑定的就是字号，只是基数错了，调了也还是很小。

另外字号调大后作者的文字框可能放不下：第一次画的时候按实际文字（和编辑器里的静态文字，再留 10%）
量一下，放不下就以中心为准放大，之后固定。

## 壁纸库

菜单栏"壁纸库…"（或显示器子菜单"从壁纸库选择…"）：扫描壁纸文件夹（默认 `~/wp`，可以添加、移除，存在
`libraryFolders`）里的全部项目，显示总数和各类型数量，按类型筛选、按标题搜索；卡片显示预览图缩略图（480 像素，
动图取第一帧）、类型和"当前"标记，点一下设为所选显示器的壁纸，右键可以打开壁纸设置、在访达中显示。
本机扫描结果：共 60 个（场景 24、视频 29、网页 7）。

开发截图（`MACWALLPAPER_LIBRARY_SNAPSHOT`）不加载缩略图、不显示标题：预览图和标题里可能有不适合查看的内容，
截图只用来检查布局。

# 文字清晰度：贴图跟着实际绘制尺寸（2026-09-28）

用户反馈时钟看不清、字糊在一起。查下来是三件事叠加，前两件是缺陷：

1. **文字贴图的分辨率是建场景时按当时的屏幕尺寸定死的**。显示器的像素尺寸一变（改缩放、换分辨率、
   把壁纸换到另一块屏），贴图不重建，绘制时就会被放大或缩小，糊成一片，特效缓冲（同样按屏幕尺寸分配）
   还会被二次重采样。现在 `TextLayer` 每次绘制都比一下"画布 → 像素"的比例，差超过 10% 就按新比例重画；
   `SceneContent` 在显示尺寸变化时按新尺寸重建整个场景。
2. **文字贴图没有 mipmap**，缩小显示时线性取样会糊。现在生成 mipmap（绘制端用的采样器本来就有 mip 过滤），
   即使贴图和显示尺寸不完全一致也能平滑降采样。
3. **时钟上的 shine 特效自带辉光**：去掉它文字是锐的，留着是带光晕的（两种情况都渲染出来对照过）。
   这一条后来单独处理了，见下面的"时钟上的辉光会把字糊掉"（原因已找到：特效缓冲的空间不对）。

还没有处理的文字字段：`brightness`（`3550149640` 的三层是 1.4 / 1.98 / 2.39，白字乘上去会截到 1，
看不出来差别，含义待核对）、`castshadow`（语料里都是 false）、`clampuvs`、`maxrows` / `limitwidth` / 省略号。

# remapvalue 算子（2026-09-28）

把输入值归一化后映射到输出区间，再用 Assign / Multiply / Add / Subtract 作用到某个粒子属性上。
官方文档（Particle Component - Operators → Remap value）写清了语义：输入区间"内部归一化成 0.0–1.0"，
输出区间的两个端点就是新的值（Multiply 时是"原值 × 这个系数"），两个 Clamp 开关分别钳制输入和输出。

## 真实数据里的字段与我们的理解

语料里 15 处 `remapvalue`（都在雨滴类系统），WE 自带还有一个预览场景。两边的字段刚好互补，印证了几个理解：

| 写法 | 例子 | 我们的理解 |
|---|---|---|
| 给了 `input` | 预览场景：`input: distancetocontrolpoint` + `inputcontrolpoint0: 1`，`inputrange` 150–200，`output: color`，输出 1 0 0 → 0 0 1 | 输入取粒子属性/全局值，按 `inputrange` 归一化 |
| 没给 `input`，给了 `transformfunction` | 雨滴：`output: velocity`，输出 -200 -100 0 → 200 -1000 0，`simplexnoise`，`transforminputscale: 10` | 输入由 transform function 生成（0–1 的噪声/波形），所以 `inputrange` 也一起省略了 |
| `operation` | `remap`（也有整个字段省略的，按 `remap` 处理） | 相当于文档里的 Assign：按输出区间取值后覆盖 |
| `flags` | 雨滴里 `output: speed`、输出 -5 → 7 的那处是 `flags: 3` | 第 0 位 = 钳制输入、第 1 位 = 钳制输出（对应文档里的两个 Clamp 开关） |

支持的输入：`speed`、`lifetime`（`age`）、`time`（`runtime`）、`size`、`alpha`、`rotation`、
`distancetocontrolpoint`（控制点编号写在 `inputcontrolpoint0…7` 里）。输出：`velocity`、`speed`
（改模长、方向不变）、`color`、`size`、`alpha`、`rotation`、`position`。认不出来的输入/输出名字记进
`unsupported`，不静默丢掉；输入和 transform 同时写时按 input 处理并记一条（真实数据里没有这种）。

## 结果

- WE 自带的预览场景 `scenes/particleelementpreviews/remapvalue` 渲染出了文档描述的效果：
  离控制点近的粒子红、远的蓝（150–200 的输入区间）；
- `~/wp` 的雨滴场景（3576135309）不再跳过这 18 处，水珠除了下落还带上了横向漂移，
  和那两处 `velocity` / `speed` 的参数一致；
- 24 个场景仍然 24/24、0 失败；不支持清单里的"粒子算子 remapvalue"整项消失。

顺带修掉一个一帧延迟：算子里改 `size` / `alpha` 时写的是"本帧绘制值"，而 remapvalue 一开始写的是粒子属性，
导致本帧的绘制值要等下一帧才生效（测试里量出来正好差一步寿命）。

# 场景对象接口：让框架级脚本动起来（2026-09-28）

`~/wp` 里 3 个幻灯片场景挂的是作者写的"幻灯片控制器"（EasyTransitions+ 9 KB）：它要遍历子图层、
改透明度和缩放、按名字取别的图层、还要调整绘制顺序。以前这些字段只按静态值画（所有图片叠在一起），
现在跑起来了。

## 运行时图层状态（`SceneState`）

每个场景对象有一份运行时状态：`origin` / `scale` / `alpha` / `color` / `visible` 和绘制序号，
外加构建时的值（算增量用）。图层自己的属性脚本、场景对象接口改的都是这份状态，绘制时按它算：

- 位置/缩放变了：把"当前世界变换 × 构建时世界变换的逆"乘在投影前面（四边形、木偶网格、文字、
  粒子都跟着动）；父图层动了，子图层因为按父链重算世界变换，也一起动（补上了以前记的那条限制）；
- 透明度/显隐/颜色：直接取状态里的值；
- `sortLayer(layer, index)`：给图层一个绘制序号，绘制时按它重排（幻灯片靠它把下一张压在当前张上面）。

没被脚本碰过的图层 `hasModifications` 为 false，绘制时直接用构建时的值，不额外算。

## 脚本侧的接口

JavaScriptCore 侧不用 `JSExport`，而是把图层对象写成一小段 JS（`Layer` 类），属性读写转到几个宿主块上
（`__layerAlpha` / `__layerSetOrigin` / `__layerChildren` / `__sortLayer`…），`thisObject` 是自己的图层、
`thisScene` 提供 `getLayer(name)` / `getLayerIndex(layer)` / `sortLayer(layer, index)`。
这样 `img.alpha = 0`、`img.origin = new Vec3(...)`、`thisObject.getChildren()` 这些写法都能直接用。

属性脚本"不给自己那个属性返回值、只改别的图层"是 WE 的正常写法（幻灯片控制器就是这样），
所以这种不算失败、也不上报；真正跑不了的（被安全检查拦下、抛异常、超时）才记进 `unsupported`，
**这一项从 10 处降到 7 处**（6 处是把拖拽脚本挂到布尔 `visible` 上的，WE 里同样跑不出结果；
1 处是 Lucy 那个 48 KB 的动画调度器）。

## 结果

- `3723993802`：9 张图按"淡入 2 秒 + 停留 2 秒"轮播（`init` 里先把所有图 alpha 清零、
  只留第一张，所以不再是一叠图），和预览图的差异 **63.9 → 29.5**；另外两个幻灯片场景同样变好
  （69.9 → 64.6、69.9 → 44.1）；
- 24 个场景仍然 24/24、0 失败；"不翻转更接近"从 19 个增加到 20 个。

注意：渲染工具每个时间点只画一帧，而幻灯片脚本按 `engine.frametime` 自己累计时间，
所以用工具核对时要给一串密集的时间点（每 0.25 秒一个）；应用里每帧都渲染，正常轮播。

`~/wp` 里只有 Lucy 有摄像机对象：`zoom` 从 3 倍（第 0 帧）拉到 1 倍（第 36 帧，12 fps、60 帧、single），

# 鼠标悬停（2026-09-28）

桌面窗口本来就忽略鼠标事件（点按壁纸要能透到桌面），所以拿不到 enter/leave。
现在用全局鼠标位置（`NSEvent.mouseLocation`，场景每帧已经在读）合成事件：

- 每帧把鼠标位置换算成画布坐标，判断它在哪个图层的四边形里（凸四边形，允许旋转）；
- 进出图层时给脚本发 `cursorEnter` / `cursorLeave`，在里面移动时发 `cursorMove`，
  事件对象带 `worldPosition`（画布坐标）；
- Lucy 时钟的 `scale` 脚本（`cursorEnter` 设 `hoverScale`、`update` 用 `engine.frametime` 平滑趋近）
  现在真的会在鼠标移到时钟上时放大、移开缩回；
- 点击类事件见下一节：用全局鼠标监听补上了。

# 鼠标点击与拖动（2026-09-28）

桌面窗口忽略鼠标事件（点按要能透到桌面），所以点击和拖动同样用全局监听
（`NSEvent.addGlobalMonitorForEvents`，`Sources/DesktopHost/GlobalMouseMonitor.swift`）旁听一份：
按下、抬起、拖动、移动都换算成这块屏幕上的 0–1 位置交给渲染器。

- **按下即捕获**：按下时记住鼠标指着的那个图层，拖动和抬起都还送给它（快速拖动时鼠标会跑出图层）；
  抬起时如果"按下到抬起够快、也没怎么移动"，再合成一次 `cursorClick`；
- `event.worldPosition` 是真正的 `Vec3`（脚本会调 `.add` / `.subtract`）；命中判断用的是图层**当前**的四边形
  （脚本改过位置也跟得上）；
- 有场景状态时 `thisLayer` 是**活图层代理**：`thisLayer.origin = …` 会真的移动图层。以前它是个副本，
  拖拽脚本写了也不生效——这是这次修掉的一个真 bug；
- 鼠标移动（不按键）也会触发一次重绘，所以静止的场景同样能响应悬停。

# 时钟被屏幕切掉：文字图层挪进可见区域（2026-09-28）

用户报的现象：**有些时钟显示在屏幕外面**，超出了屏幕边界。

## 原因（已核对）

铺满裁切（`SceneRenderer.coverProjection`）。屏幕 3024×1964（1.54:1），而这个场景的画布
4951×2555（1.94:1）：短边撑满（scale = max(3024/4951, 1964/2555) = 0.7687），画布两侧各被切掉约 7%
——屏幕上真正看得见的画布范围是 x 509…4442。3560362683 的"Time & Date"中心在 x 4277、框 830×290，
即 x 3912…4692，右边约 250 个画布单位（两行数字里右侧那部分）落在屏幕外。

**这是 WE 自己的行为，不是我们独有**：WE 的设计文档明确说画布比例和显示器不一致时会切掉画面两侧
（"Wallpaper Engine will cut off the sides of your wallpaper once you apply it to your desktop"，
见 `REFERENCES.md`）。所以铺满裁切保留，只对**文字图层**做边界保护——时钟是拿来读的，被切掉一半会
直接读不出内容，其余画面照旧铺满。

## 做法

- `SceneRenderer.visibleRegion(canvas:target:)`：铺满裁切后画布上真正看得见的那块矩形
  （屏幕比例和画布比例一致时就是整块画布，等于不做任何事）；
- `SceneRenderer.fitOffset(lo:hi:regionMin:regionMax:)`：把一个矩形挪进可见区域要加的画布坐标偏移。
  放得下就贴边挪，比可见区域还大就居中（这时挪也挪不进来，居中至少让它两边一样多）；
- `SceneRenderer.placedInView(world:size:region:)`：文字图层的框超出去时，返回挪进去以后的世界变换。
  在**构建时**（`makeTextDraw`）做——那时目标屏幕尺寸已知，挪完写回 `state.setBuildWorld`，
  于是顶点、鼠标命中、特效链的 `g_EffectTextureProjectionMatrix` 全都跟着挪后的位置走；
  脚本驱动的位置、缩放仍然按增量叠在它上面（`delta = world(now) × buildWorld⁻¹`），拖动照样工作。
- 摄像机不算在内：`visibleRegion` 用的是默认取景（zoom 1、origin 0）的可见范围，作者的开场镜头动画
  该把画面推出屏幕就推出去，那是作者的意图。

## 结果（3024×1964，即本机屏幕）

| 场景 | 文字图层 | 处理 |
|---|---|---|
| 3560362683 | "Time & Date"（中心 x 4277） | 挪 -250：两行数字都完整落在屏幕里，右侧留出框内 10% 的余量 |
| 3521337568 | "Clock"（框 x 338…765） | 本来就在可见区域（x 257…3583），不动 |
| 3535216365 | "Date" / "Clock"（框右边界 x 4854） | 可见区域到 x 5003，不动（本就贴边但不切字） |
| 3550149640 | "DAY DATE TIME (EN)" / "Date" / "Clock" | 不动 |
| 3646225957 等 6 个拖拽时钟 | "时间" | 脚本挂在 `visible` 上、宿主跑不了 → 默认隐藏（见上一节）。把 `show` 属性打开让时钟出现后，它们也会被挪进来：3664111408 挪 (-251, -37)、3646359445 挪 (-243, -23) |

核对工具：`WallpaperTool render-folder` 现在支持 `TARGET_HEIGHT`，给了 `TARGET_WIDTH` / `TARGET_HEIGHT`
就按屏幕尺寸出图，看到的就是屏幕上真正显示的样子（含铺满裁切）：

```
TARGET_WIDTH=3024 TARGET_HEIGHT=1964 swift run WallpaperTool render-folder <解包目录> ~/wp-assets out.png 5
```

不给 `TARGET_HEIGHT` 时还是按画布比例出图（和 WE 的预览图对比时用这个）。

## 补充（2026-09-30）：画布比内容大时不露空边

用户反馈 3681810302 "没铺满屏幕"：作者声明画布 4000×2650，背景图只有 4000×2508，顶上 142 单位没有任何图层；
在 3024×1964 的屏上铺满裁切看得见画布 y 26…2623，于是顶上露出约 84 像素的清屏色（0.7 灰）。

- `SceneRenderer.fillBox(canvas:content:)`：画布与内容包围盒（`contentExtent`）的交集，只在它盖住画布
  ≥ 88% 面积时才给——内容只占一小块的场景（时钟、单张小图）不能为了不露边被放大；
- `SceneRenderer.framing(canvas:center:fill:target:)`：先按原来的铺满裁切算取景；**只有取景超出了有内容的框**
  才动——先平移进框里，框比取景还窄的方向再放大到刚好不露。屏幕比例本来就把空边切掉时（16:9 屏上的同一场景、
  横屏上的 2989540197）取景和 WE 完全一样；
- 投影、文字图层的边界保护（`visibleRegion(canvas:center:fill:target:)`）、特效缓冲的屏幕比例
  （`canvasScale(target:)`）都用同一个取景；`canvasSize` 仍是作者声明的画布（脚本的 `engine.canvasSize`、
  摄像机的缩放中心都按它）。

第一版（fcc1fb6）是把画布直接换成交集，在任何屏幕上都生效：2989540197 在横屏上本来看不到空边，也被整体
上移了 108 个画布单位；画布中心和 `canvasSize / 2` 也不再一致（摄像机缩放中心、文字边界保护还按作者画布算）。

## 测试

`Tests/SceneRendererTests/TextLayerTests.swift` 的 `TextStaysInsideTheScreenTests` 5 个：

- 画布比屏幕宽时，贴右边的时钟被挪回屏幕里（墨迹完整、不贴边）；
- 画布比屏幕矮时，贴顶边的时钟被挪下来；
- 屏幕比例和画布一致时**不动**（锁住"不无故挪动作者摆好的位置"）；
- `visibleRegion` 与 `fitOffset` 的几何表（贴边挪、居中、几种边界）。

前两个像素断言在关掉边界保护后确实失败（时钟整个落在屏幕外，一个像素都看不见），不是空跑。

# 时钟上的辉光会把字糊掉（2026-09-28，原因已找到，见文末"修正"）

接上一次"文字贴图跟着实际绘制尺寸"，用户反馈 **Lucy 的时钟还是糊的**。这次查到的是另一件事：

## 现象与定位

- 把时钟上的特效去掉，文字是**锐的**（同一时刻渲染出来对照过）→ 不是贴图分辨率、不是排版；
- 糊来自作者给时钟挂的 **shine 特效**：`tools/…` 里量到的中间结果是
  **rays 的 rgb ≈ 1.0、alpha ≈ 1.0**（辉光在被点亮的文字那一带整个饱和），
  combine 的 `albedo.rgb = ApplyBlending(BLENDMODE, albedo.rgb, rays.rgb, rays.a)`、
  `albedo.a = saturate(albedo.a + rays.a)` 于是把**字与字之间的透明像素一起涂白**——
  数字和日期糊成一团。按实测的中间值代公式算出来的结果和最终画面逐点吻合（差几个百分点），
  说明是我们的实现在忠实执行这套数学，不是管线接错。

## 和 WE 的一致性（这一步只能查到这）

- WE 自己给这张壁纸编译过的着色器缓存在 `~/wp/<id>/shaders/blobsSM40/*.dxs`（SHDV + DXBC，
  是 WE 在 Windows 上编的）。在 **shine cast** 的 blob 里能找到 `1/7`（8 个采样的权重）和
  `0.375`（`sampleIntensity = 0.1 × 30 / 8`）这两个常量 → WE 跑的是同一套数学，常量也对得上；
- WE 的官方文档在 **Shine**（以及 Godrays）里写着：给**透明图层（图片、文字）**用这个特效
  "会混得不对，效果很差"，要开 **Copy background** 才好。作者给时钟**没有**开
  （两个图片图层的 shine 反而配了遮罩 + 0.71 / 0.84 的高阈值）；
- 我们当时以为"WE 也会糊"。**2026-09-28 用户给了 Windows 上 WE 的 4K 截图**（`~/Downloads/win_we/`），
  同一张壁纸同一个位置：**WE 的时钟是干净的，完全没有辉光**。所以上面这条推断是错的，
  糊是**我们这边和 WE 的差异**，不是作者的参数问题。

## 真正的原因（修正）

我们算特效链用的是**图层自己尺寸**的缓冲：文字的链子只有文字框那么大（440×199 画布单位），
`raylength = 0.1` 于是只铺开 ~22 像素，全落在字上，辉光饱和成一片白 → 字被糊掉。
**WE 是用"合成空间"算的**：`effect.json` 里 fbo 的名字就是 `_rt_HalfCompoBuffer1/2`
（blurprecise 用的是 `_rt_FullCompoBuffer1`），也就是**整屏**尺寸，图层只是画在它的位置上；
`raylength = 0.1` 在 3840×2160 里铺开 ~190 像素，绝大多数采样落在字外面，
累加出来的 alpha 只有零点几 → 字保持清晰、外面只剩一层很淡的光。

验证（把文字图层的特效空间临时放大到整张画布，其它什么都不改）：**辉光消失，和 WE 截图一致**。
这与另外两条观察也对得上：WE 跑这类壁纸的内存明显比我们大（合成尺寸的缓冲），
以及 `g_EffectModelViewProjectionMatrix`（把图层摆到合成空间里）这个常量的存在。

## 处理（2026-09-28 已实现）

**图层特效链的缓冲改成合成（整屏）尺寸**（`DrawListBuilder.compositionSize` / `screenSpaceChainSize`）：

- 图片、形状、文字这三类图层的链子按**屏幕像素尺寸**分配缓冲，拷贝那一步用图层自己的屏幕投影
  （`g_EffectModelViewProjectionMatrix` 的那份矩阵）把图层画进自己的位置，缓冲其余地方是空的；
- 画的时候按顶点在屏幕上的位置去取结果（`Draw.screenSpaceChain` + 顶点 UV 换成屏幕 UV）；
- 合成层、被别的特效引用的隐藏图层、木偶网格保持原来的图层尺寸（取回的坐标是网格/图集坐标，
  另做要动的地方更多，先留到以后）；
- 离屏工具（没给目标尺寸）行为不变，还是按图层尺寸算。

于是 `raylength = 0.1` 在 3840×2160 里铺开约 190 像素，绝大多数采样落在字外，
时钟和 WE 截图一样清楚（只留很淡的一层光）。验证：Lucy 在 3840×2160 下逐点比过，
没有特效的 6 个场景（3646225957 等）逐字节不变，`swift test` 全过（新增
`effectsOnLayersRunAtTheSizeOfTheScreen`、`effectsWithoutATargetSizeStillUseTheLayer` 锁住这个尺寸）。

代价与遗留：

- **显存**：Lucy 在 4K 目标下构建后约 600 MB（以前按图层尺寸只有三百多），和 WE 的量级一致；
  再往下要像 WE 那样做**共用缓冲池**（每条链两份整屏份在主缓冲上还是偏多）；
- 木偶网格图层、合成层上的特效仍然是图层尺寸；
- 还剩一处小差异：把场景里存的参数都算上时，时钟外面比 WE 截图**多一层很淡的光**；
  如果只用着色器默认值（`rayintensity` 1，而不是场景里存的 2）渲染，和 WE 截图基本一致。
  也就是说 WE 可能没有应用这份工作坊特效实例上的参数覆盖（原因待核对，先保留作者的值）。

# 语料扩到 447 个壁纸后补掉的兼容问题（2026-09-28）

用户新加了一批壁纸，全量跑一遍（`WallpaperTool scan` + `render-scenes`，447 个）暴露出几类问题。
这一轮修掉的三类（都在真实语料上验证过）：

1. **系统字体**：WE 的编辑器里可以直接选系统字体，场景里存成 `systemfont_arial`、`systemfont_consolas`
   这种名字，我们当文件名去找，读不到就没有文字（3 处）。现在按名字映射到 macOS 的同名字体，
   没有的（Windows 独有的 consolas 等）按分类退回相近的：等宽退 Menlo / Monaco，无衬线退 Helvetica Neue / Arial，
   衬线退 Times。
2. **特效引用排在后面的图层**：`_rt_imageLayerComposite_<编号>_a` 引用的图层如果排在引用者**后面**，
   以前只记一句"它要排在引用者前面"然后跳过（6 处）。WE 允许这种顺序，现在按需先把那个图层
   （连同它自己的特效）建出来，结果放进 `composites` 缓存，主循环轮到它时直接复用，不会建两遍。
   互相引用有 `buildingComposites` 兜底，不会转圈。
3. **着色器的两处方言差异**（`ImplicitConversionFixer`，8 处）：
   - **浮点取模**：WE 按 HLSL 的规则写，`frequency % RESOLUTION` 这种浮点 `%` 是合法的；
     GLSL 只允许整数。现在按报错把那一行改成 `mod(frequency, float(RESOLUTION))`
     （HLSL 的 `%` 对浮点就是 fmod，负数下和 `mod` 有差别，语料里都是正数）；
   - **内置函数的参数截断**：`mix(vec4, vec3, float)` 这种在 HLSL 里会自动截断，GLSL 报"没有匹配的重载"。
     现在按源码里声明过的维度，把最长的参数截到最短的（`albedo` → `albedo.rgb`）。

结果：字体失败 3 → 0，特效翻译失败 14 → 5（剩下的见下）。

## 还没有修的（按影响排序）

- **木偶模型读不了（31 处）+ 木偶骨骼读不了（4 处）**：`.mdl` 只支持过 Lucy 那一个顶点格式
  （`0x0180000F`，80 字节），新语料里还有别的格式，读不懂就整块不画（人物缺件）。要拿新样本
  逐字节核对格式定义；
- **粒子算子**：`oscillatesize` 55、`colorchange` 30、`vortex` 23、`rope` 18、
  `mapsequencebetweencontrolpoints` / `mapsequencearoundcontrolpoint` 各 6，另外 `eventspawn` 子系统 1 处；
- **透视（3D）场景 3 个**：直接判"透视场景还不支持"，显示测试图案；
- **5 处特效翻译失败**：`x_ray_plus`（`vec4 color =0,color_2=0;` 这种一行多个声明符被改坏了）、
  `bloom` / `audio_responsive_oscilloscope`（两个 varying 拿到同一个 location）、
  `contrast_based_sharpness`（一行语法没认出来）、`effects/motionblur`（材质读不到）；
- 上一轮记下的三项：木偶网格/合成层上的特效仍是图层尺寸、共用缓冲池、`rayintensity` 那处待核对的光。

## 第三轮（2026-09-28 晚）：又修两处着色器方言差异

- **数组 varying 的 location**：`varying vec2 v_TexCoord[4];` 这类数组会占连续 4 个 location，
  改写器只往前推了 1，后面的 varying 拿到同样的位置，glslang 报 "overlapping use of location 1"
  （`bloom`、`audio_responsive_oscilloscope`）。现在按元素个数推进计数器，两处都通过了。
  注意：片段里同名的非数组 varying 只占 1 个位置，采样到的会是第一个元素而不是中心，
  语义上和 WE 有差（先记着）。
- **一行多个声明符**：`vec4 color = 0, color_2 = 0;` 里初始化用了整数，glslang 会把错报成
  "undeclared identifier"。`ImplicitConversionFixer` 现在会把这种语句拆成多条独立声明，
  各自再按常规补转换（`x_ray_plus` 还没通，报错没有走到这条分支，待查）。
- 另外加了个调试开关：`DUMP_FAILED_SHADERS=1` 时把翻译失败的那一阶段改写后的源码写到
  `/tmp/macwallpaper-shader-<stage>.glsl`，方便对着报错行看。

剩下的编译失败：`x_ray_plus`（上述分支没生效）、`contrast_based_sharpness`（一行语法没认出来）、
`effects/motionblur`（材质读不到）。

## 木偶模型：MDLV0013（老版本）支持（2026-09-28）

新语料里 35 处"木偶模型读不了"，全是 **MDLV0013**（我们只支持过 Lucy 的 MDLV0023）。逐字节对比
`meion hatsunemiku magicalmirai 2020` 系列后看出差别：

- 老版本**没有单独的顶点格式字段**：材质路径（加 0 填充）之后直接是"顶点区字节数"，然后就是顶点；
- 顶点 **52 字节**：位置 3f、骨骼编号 u32（一根）、法线 3f、权重 4f、纹理坐标 2f。
  核对依据：每组权重和为 1、纹理坐标都在 0–1、索引都小于顶点数，字段和 MDLV0023 一一对应；
- 动画段结尾的填充：MDLV0023 是 35 个 0 字节，**MDLV0013 只有 4 个**（按 35 读正好多读 31 字节，
  段尾对不上）。

后来又补了三种情况，木偶类问题从 35 处降到 **0**：

- **MDLV0014** 和 MDLV0013 一样没有格式字段（材质路径之后直接是顶点区字节数），归到同一套老布局；
- **顶点格式 0x01800009**（MDLV0016 等）：没有法线和切线 = 位置 + 骨骼 4×u32 + 权重 4f + uv = 52 字节，
  和 0x0180000F（80 = 52 + 法线 12 + 切线 16）正好对得上；
- 有的 MDLV0016 文件在格式字段**前面还多一个 u32**（值是 4），现在改成从材质路径往后找第一个认识的

## iris_movement__：多余的 #endif 与 HLSL 的向量维度提升（2026-09-28）

最后一个翻译失败的 `iris_movement__` 连着踩了两个坑，都和"HLSL 容忍、glslang 不容忍"有关：

- **结尾多余的 `#endif`**：`workshop/2973943998/effects/iris_movement__.vert` 里
  `#if FOLLOWCURSOR`（第 76 行）已经在第 91 行 `#endif` 收掉，第 93 行又多写了一个，
  条件编译深度一路掉到 −1。WE 的编译器不管，glslang 直接报 `'#endif' : mismatched statements`。
  `ShaderAssembler` 现在在展开 `#include` 之后按行统计深度，把深度已经归零时多出来的 `#endif`
  丢掉（`balancingConditionals`）；正常成对的条件编译块原样保留。
- **`vec4 * vec2`**：HLSL 里两个不同维度的向量做二元运算时按**较大**的维度算，多出来的分量丢掉
  （`vec4 * vec2` 等价于 `v.xy * s`）；GLSL 报 `wrong operand types: no operation '*' exists`。
  `ImplicitConversionFixer` 现在会从报错里读出两侧的维度（`4-component vector of float`），
  再用和"取模改写"同一套括号配平扫描找出两侧操作数，把较大的那个截短成 `.xy` / `.xyz`
  （`truncateOperandsForOperator`）。顺带把这段扫描抽成了共用的 `binaryOperandRanges`。

全量 447 个：**特效翻译失败 1 → 0**，`iris_movement__` 现在正常画出。

## 粒子画法：rope 与 ropetrail（2026-09-28）

`~/wp` 的 447 个场景里，**21 个用 ropetrail、14 个用 rope**（共 47 + 18 处），之前都是
"按精灵近似"（拉长的精灵），属于明显的画错。现在两种画法都按 WE 官方粒子文档实现成**带子**：

- **rope**（"draws a line between each particle that is spawned"）：把先后出生的粒子连成一条带子。
  粒子数组会因为死亡换位，所以按**出生编号**排序再连；宽度取各粒子的大小，颜色和透明度也取各粒子自己的
  （所以一条带子会从宽到窄、从亮到淡地渐变）。
- **ropetrail**（"draws a line along the path of each particle"）：沿每个粒子走过的路径画带子。
  模拟时每一步往粒子的位置历史里记一条（位置 + 当时的大小和透明度），历史是**定长环形缓冲**
  （容量 = 参数 `length` / 模拟步长，上限 64 条），一步 O(1)，不会每帧搬内存。
  记的是"最终画出来的位置"，所以算子的偏移和 eventfollow 的父粒子偏移都在里面。

几何与参数（对照官方文档与文档站上的两个演示视频 `particle_renderer_rope.mp4` /
`particle_renderer_rope_trail.mp4`）：

- **顶点约定**：WE 的 genericparticle 顶点着色器把位置算成
  `a_Position + size * (right * (u - 0.5) - up * (v - 0.5) * ratio)`。引擎自己画带子时，
  把算好的顶点位置塞进 `a_Position`、大小填 0，于是着色器原样输出位置——我们照这个约定生成顶点。
- **宽度**：横截面半宽 = 粒子大小的一半，横向在 xy 平面内取路径法线（拐角用前后两点的平均方向）。
- **贴图方向**：v 沿带子、u 横跨 0–1。`~/wp` 里这类贴图都是 32×128 / 256×512 的细长图
  （drop、beam、light_shafts），v 沿带子才和精灵画法里"长边顺着运动方向"一致。
- **uvscale**：当成"整条带子上把贴图铺几次"，默认 1（整条一张）。演示视频里的带子是一条亮芯、
  两端渐隐的**连续**弧线，没有逐段的重复；这也是官方 `uvsmoothing`（按长度均匀铺、避免跳变）的存在意义。
- **subdivision**：官方写的是"每条线上的细分数，越大拐角越圆"，所以用 **Chaikin 切角**实现
  （每段在 1/4、3/4 处切开，重复 subdivision 次）。默认 3：`~/wp` 里显式写过 0 和 3，
  而演示视频里几个粒子就能连成流畅的圆角弧线。切角不会像样条那样冲出去。
- **uvscrolling**：WE 没有公开速度，按"每秒沿带子滚一格"实现（`~/wp` 里没有场景用到这个开关）。

带子也用 WE 自己的 `genericparticle` 着色器画，只是采样器换成 **repeat**——WE 文档要求这类贴图
"关掉 clamp"，否则贴图会被切掉（我们的精灵路径用的是 clampToEdge，uv 在 0–1 内不受影响）。

拿 WE 自带的两个预览场景（`~/wp-assets/scenes/particleelementpreviews/rope` 与 `ropetrail`）
对照着调过：rope 出来的是一圈圆角带子，ropetrail 出来的是沿粒子路径的流线，和演示视频里的形态一致。

## 粒子初始化：mapsequencearoundcontrolpoint / mapsequencebetweencontrolpoints（2026-09-28）

这两个初始化器是"把一串出生点摆到控制点周围或控制点之间"，`~/wp` 里各 6 处（7 个场景），
之前整条跳过。按官方文档实现：

- **Position around control point**：粒子到控制点的**距离保留**（半径还是发射器给的），
  只把角度摆到序列的第 i 格上。文档原话说"Make sure to also bind your emitter to the same control point,
  otherwise the size of the circle will change depending on the distance to the control point"，
  正好印证半径就是"粒子到控制点的距离"。
  `speedmin`/`speedmax` 是出生时的速度向量，写了就盖掉发射器给的速度（樱花那处是 `0 100 0`，花瓣往上飘）。
- **Position between control points**：位置插值到控制点 start 与 end 之间。放电那几处就是靠它把闪电铺在
  两个控制点之间，而控制点由场景里的 `controlpoint1` 覆盖值给出。
- 两者共用的字段：`count`（有几个出生点）、`bounds`（起点和终点的比例，整圈/整条是 `0 1`）、
  `limitbehavior`（`repeat` 绕圈、`mirror` 折返）。序列每出生一个粒子往前走一格，走完一轮回到起点。

还没做的是文档里两个"高级"开关（`reduce outer positions / velocity / size`、`enable arc`），
`~/wp` 里的 12 处都没有用到。

## 脚本宿主：按 WE 的 IEngine 文档补齐接口（2026-09-28）

以前脚本跑不起来时只报一句"脚本没有运行"，看不出原因。现在 `SceneScript` 会带着**失败原因**
返回（载入异常、超大、安全检查拦下都会写进 `problem`），渲染报告里的 ✗ 行就能直接看到为什么。
顺着这条线索修掉了三处会让整段脚本失败的问题：

- **`engine.isRunningInEditor` 写成布尔属性**：WE 的 IEngine 文档里它是**函数**，
  脚本里 `engine.isRunningInEditor()` 直接抛异常（Lucy 那个 48 KB 的 NSL 脚本就是这么挂的）。
  现在按文档补齐了 engine 上的常量（`AUDIO_RESOLUTION_16/32/64`）和判断类函数
  （`isDesktopDevice` / `isMobileDevice` / `isWallpaper` / `isScreensaver` / `isPortrait` /
  `isLandscape` / `isRunningInEditor` / `openUserShortcut`）、`screenResolution`，
  以及 `setTimeout` / `setInterval`（按脚本自己的 runtime 计时，返回值是取消函数）。
- **`engine.registerAudioBuffers`**：音频律动脚本在载入时就会调它。我们还没接系统音频采集
  （要权限），所以给一个全 0 的 `AudioBuffers`（`average` / `left` / `right`），
  脚本能正常载入、按"静音"的样子显示，而不是整段脚本失败退回静态值。
- **`thisLayer.size`**：活的图层代理上缺这个属性（脚本用它算"碰到屏幕边界"），
  一起补上（`SceneGraphScriptAPI.layerSize`）。
- **`withoutModuleSyntax` 认不出压缩过的脚本**：以前只匹配行首的 `export`，
  `"use strict";export var …` 这种一行写完的会报 `SyntaxError: Unexpected keyword 'export'`
  （3372715909 的时钟脚本）。现在前面是行首、分号或花括号都认。

全量 447 个：Lucy 的 ✗ 消失（NSL 脚本能载入了），"文字脚本" 2 → 0，
"脚本驱动的字段" 14 → 11。剩下的 ✗ 里，6 个是同一份"拖拽脚本挂在 visible（布尔属性）上"
的写法（脚本自己对布尔值写 `.x`，WE 那边同样会抛错），另外几个要么用到 `thisScene.createLayer`
（运行时建图层，还没做），要么是透视场景。

## 视频纹理（`.tex` 里装的是 MP4）（2026-09-28）

用户反馈"有些壁纸显示不出来"。查到一个真实原因：有的 `.tex` 载荷不是像素，而是一段 **MP4**
（`TEXB0003` 没有 `isVideo` 字段，WE 用标志的第 5 位标记：`~/wp` 里 12 张这样的纹理都是
标志 34 = 2 | 32，载荷以 ISO-BMFF 的 `ftyp` 盒开头）。我们以前按原始像素读，
字节数当然对不上，图层整块加载失败。

`TexFile.isVideoTexture` 现在认得这种情况，`TextureLoader` 用 AVFoundation 解出**第一帧**
当静态贴图用——逐帧播放还没做，但画面不会再缺一块。
3372715909 与预览图的差异因此从 109.2 降到 61.9。

## 系统音频律动（2026-09-28）

"跟着音乐一起律动"以前完全没有：音频律动的特效拿到的 `g_AudioSpectrum16Left[16]` 是没绑定的数组
（恒为 0），脚本的 `engine.registerAudioBuffers` 也只是全 0。现在补上：

- **采集**（`DesktopHost/SystemAudioSpectrum`）：Core Audio 的**进程 tap**——`CATapDescription` 的
  全局立体声 tap（`initStereoGlobalTapButExcludeProcesses`，macOS 14.2+）抓系统输出，
  挂到一个私有聚合设备上，`AudioDeviceCreateIOProcIDWithBlock` 读样本。这条路不需要屏幕录制权限，
  第一次用只会弹一次"系统音频录制"的授权（Info.plist 要有 `NSAudioCaptureUsageDescription`）；拿不到就按静音处理。
  只有用到音频律动的场景在播放时才采集（`acquire` / `release` 引用计数），暂停、换壁纸就停。
- **分频**：1024 点 FFT（vDSP），按 20 Hz–16 kHz 做 **16 / 32 / 64 段对数分频**（WE 的
  `g_AudioSpectrumNNLeft/Right` 就是这个口径），每段取峰值归一化后再按时间平滑（0.35）。
- **接线**：`EffectChain.encode` 每帧把三档频谱写进 uniform（含这些 uniform 的链标记成每帧重算，
  否则会被当成静态链只算一次）；`SceneScript.refreshAudio` 每帧把 64 段频谱推给脚本里注册过的
  AudioBuffers（按脚本要求的分辨率在 JS 里降采样）。
- **核对**：`WallpaperTool audio-spectrum [秒数]` 现场打印频谱——本机放声音时峰值 0 → 0.63，
  停声后逐级衰减回 0；2573849422（Bass Clock 24h）的缩放脚本随声音变化，相邻画面差 1.6 万像素。
