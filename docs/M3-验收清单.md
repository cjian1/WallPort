# M3 容器与资源层：验收清单

计划里的验收标准：**能列出用户机器上全部 WE 项目的元数据与缩略图，并正确识别类型。**

## 已实现（`Sources/WallpaperFormats`）

- `ScenePackage`：读取 scene.pkg（PKGV0020 / 0022 / 0023 实测可读），按内存映射打开，按名称取条目；
- `TexFile`：解析 TEX 纹理头、图像容器（TEXB0003 / 0004 实测）、各层 mipmap，支持 LZ4 解压，区分原始像素和内嵌图片；
- `SceneDependencies`：从 scene.json 出发沿引用链找出全部文件，分成"包里有"和"需要 WE 自带素材"两类；
- 所有读取都做边界检查，文件损坏或恶意构造时抛错而不是崩溃；
- 命令行：`WallpaperTool pkg / pkg-extract / tex / scan`。

## 验收结果（2026-09-28，`~/wp` 的 20 个项目）

```bash
swift run WallpaperTool scan ~/wp
```

| 项目 | 结果 |
|---|---|
| 类型识别 | 20 / 20 正确：场景 8、视频 5、网页 7（其中 2 个场景写的是大写的 `Scene`） |
| 预览图 | 20 / 20 可读：场景为 610–1024 像素的 JPEG，视频和网页为 160–256 像素的 GIF 动图 |
| scene.pkg | 8 / 8 可解析 |
| TEX 纹理 | 34 / 34 可解析，原始像素的每层 mipmap 字节数都和按格式算出的完全一致 |
| scene.json | 8 / 8 可解析：图片图层 18、粒子 12、文字 2、其他 2 |

## 格式事实（全部来自真实文件，未参考任何第三方实现）

- pkg：`[长度][版本][条目数]`，每个条目 `[名称长度][名称][偏移][大小]`，偏移相对于条目表之后的数据区；不压缩、不加密；
- TEX 格式编号：0 = RGBA8888、4 = DXT5、7 = DXT1、8 = RG88、9 = R8（字节数核对通过）；6 = DXT3 还没见到实例；
- 内嵌图片的 FreeImage 编号：2 = JPEG、13 = PNG；
- LZ4 是不带帧头的块格式；
- **纹理尺寸和图像尺寸经常不同**（例如 3840×2176 对 3792×2128、8192×4096 对 4386×2419），着色器里的 `g_TextureNResolution` 必须区分两者；
- 场景包外的 `shaders/blobsSM40` 是 Direct3D Shader Model 4.0 的编译缓存，说明 WE 在 Windows 上把着色器方言编成 HLSL；
- 这批文件里没有动图纹理（TEX 末尾的帧信息），也没有 DXT3，两者仍待验证。

## 对 M4 的影响

**每个场景都依赖 WE 自带素材**，包里只有项目自己的图片、特效和材质：

| 用到它的场景数 | 自带素材 |
|---|---|
| 8 / 8 | `shaders/genericimage4.vert/.frag`（图片图层的基础着色器） |
| 6 / 8 | `shaders/genericparticle.vert/.frag`（粒子） |
| 1–2 | 粒子贴图（halo、fog、rosepetals 等）、`models/util/composelayer.json`、`shaders/common.h`、两个字体 |

所以 M4 开始渲染之前，需要从 Windows 上 WE 的安装目录（`steamapps/common/wallpaper_engine/assets`）拷一份自带素材到 Mac。这些素材属于 WE，只能从你自己的安装里取，不能随产品分发，也不能放进仓库。
